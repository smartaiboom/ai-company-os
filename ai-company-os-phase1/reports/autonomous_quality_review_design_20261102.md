# AI 직원 간 자율 품질 검토·수정 루프 최소 설계

작성: 2026-11-02 12:08 KST
기준 커밋: `99d12bd9a45d4e0257fe6a18d8f1e8b5d9faaffe` (main/origin/main 일치)
범위: 분석·설계만 수행. 아래 신규 필드·함수·경로·루프는 모두 제안이며 구현하지 않았다.

## 1. 현재 코드에서 확인한 기반과 빈 부분

- `execution_engine.py:MockExecutionEngine.ROLE_INSTRUCTIONS/execute`는 역할별 문구를 생성한다. 품질 검토 담당은 '요구사항 충족 여부: 검토 필요', '추가 검증 필요' 같은 고정 문구를 반환하며 기계가 소비하는 합격/불합격 JSON을 반환하지 않는다. 독립 실행 직원 프로세스나 실제 조사·빌드 도구가 아니다.
- `app.py:_resolve_input_task_ids`, `_validate_task_predecessors`, `_build_previous_results`는 선행 업무를 ID로 연결하고 완료·비공백 결과·사용자 승인을 검사한 뒤 previous_results로 전달한다. 구형 데이터에는 입력명 매칭 호환이 있다.
- `execute_project_task`는 사용자 수정 의견을 previous_results의 '검토 수정 요청' 항목으로 전달하고 실패/빈 결과에서 기존 result를 보존한다. 성공한 완료 업무는 사용자 수정 요청·상태 변경 없이 바로 재실행할 수 없다. 자동 판정용 재실행 권한은 현재 없다.
- `task_review_controls`, `/task/review`, `task_needs_approval`은 사용자 검토·수정 요청과 마지막 업무 승인을 관리한다. 자동 검토와 사용자 승인 상태를 공유하면 자동 승인 또는 의견 소실 위험이 있다.
- `run_mock_workflow`는 mock 전용, 최대 5개, 프로젝트 잠금 안에서 실행하며 사용자 승인 대기·수정 요청·실패에 정지한다. 자동 품질 판정과 수정 반복 카운터는 없다.
- `final_evidence`, `final_execution_context`, `invalidate_final_report`, `save_project`, `archive_final_report`, `final_report_state`는 최종 실행 근거·지문·승인·보관 파일을 검사한다. 목표/결과/승인 변경 시 현재 확정이 무효가 되고 과거 JSON은 보존된다. 임의의 신규 quality 필드를 추가하는 것만으로는 현재 지문에 반영되지 않는다.
- 관련 근거 테스트: `test_execution_engine`(역할별 모의 결과/입력), `test_quality_review_flow`(선행 변경 후 검토·보고 재실행), `test_mock_workflow_orchestration`(승인 경계/상한/모드 차단), `test_concurrent_execution_safety`(프로젝트 경합), `test_final_report_approval`(수정 의견·보관·무효화·저장 오류). 이들은 실제 의미 품질 판정을 검증하지 않는다.

현황 분석 보고서의 '최종 승인 미구현/잠금 없음' 등은 당시 기록이다. 현재 구현과 최신 최종 승인 보고서를 우선한다. 최신 과거 전체 결과는 88개 중 87개 통과·브라우저 1개 skip이며 이번에는 테스트를 실행하지 않았다.

## 2. 최소 명시적 검토 관계와 대안

기존 계획의 input_task_ids에 '검토자가 생산자를 검토한다'는 관계를 새로 섞지 않는다. 다음 구조를 제안한다.

`quality_policy = {schema_version: 1, enabled: true, target_task_ids: ["TASK-002"], reviewer_id: "mock-quality-reviewer-v1", ruleset_id: "required-sections-v1"}`

reviewer_id는 서버가 허용한 **논리적인 모의 품질 담당 역할**이다. tasks에 가짜 직원 업무를 삽입하거나 다른 스레드·외부 AI를 호출하는 뜻이 아니다. 검토 대상은 사용자 요청/승인된 설정의 정확한 ID 목록이며, 임의 업무명·역할 문자열이나 '바로 앞 업무'로 추론하지 않는다. 대상 ID는 유일하고 존재해야 한다. 첫 구현은 요청당 대상 1개, 논리 검토자 1개만 허용한다. 자기 검토 관계·알 수 없는 검토자·잘못된 규칙은 판정 불가로 종료한다. 기존 tasks/ID/입력 순서를 바꾸지 않는다.

대안인 '기존 품질 검토 업무를 후속 업무로 자동 실행'은 현재 선행 사용자 승인 게이트를 먼저 통과해야 하므로 승인 전 자동 수정과 맞지 않고, 앞선 업무로 되돌아가는 실행 의존성을 넣으면 순환 위험이 있다. '모델이 검토자와 대상을 자유롭게 고름'도 결정론과 비용 통제를 해친다. 따라서 별도 품질 메타데이터를 사용하고, 기존 품질 검토 역할의 결과 텍스트는 그 자체로 통과 근거로 해석하지 않는다.

## 3. 구조화된 판정과 결정론적 기준

업무의 선택적 quality_review에 다음을 저장한다. 구형 데이터의 누락은 '미검토/미설정'이며 자동 마이그레이션하지 않는다.

| 필드 | 의미 |
| --- | --- |
| schema_version, ruleset_id, reviewer_id, target_task_id | 해석 가능한 정책과 검토 주체/대상 |
| result_revision, result_hash, input_context_hash, policy_hash | 검토한 정확한 결과·입력·규칙 식별. 같은 내용으로 재실행해도 revision 증가 |
| verdict | pass(통과), changes_needed(수정 필요), inconclusive(판정 불가) |
| checks | rule_id, expected, observed, satisfied, evidence_location을 갖는 제한된 배열 |
| feedback | 실패한 규칙 ID와 한국어 수정 지시. 판정 불가이면 그 이유 |
| checked_at, review_id | KST 시각과 고유 감사 식별자 |
| outcome/status | 평가 작업의 succeeded/error/interrupted/stale를 판정값과 구분 |

mock 규칙 첫 버전은 서버의 고정된 '필수 제목/구획 존재' 검사만 한다. 예: 요구사항으로 명시된 제목 '목표', '결과', '미확인 사항'이 독립된 줄/Markdown 제목으로 존재해야 함. substring 우연 일치나 입력 설명에 들어 있는 단어는 통과 근거로 세지 않는다. 필수 구획의 정의는 사용자에게 표시하며 테스트 fixture도 같은 공개 규칙을 사용한다. 규칙 없는 자유 문서는 판정 불가다. 비공백 업무 결과가 있지만 필수 구획이 없으면 수정 필요, 모두 있으면 형식 검사 통과다. 실무 사실성·근거의 진실·요구사항의 의미적 충족까지 통과했다고 표시하지 않는다.

결과가 빈 문자열/잘못된 타입, 성공 이력 없음, 업무가 미완료/재검토 중, 입력/정책이 유효하지 않으면 판정 불가이며 수정 실행을 시작하지 않는다. 평가 함수 예외·빈 판정·알 수 없는 enum·누락 checks/feedback·과도한 응답은 error+inconclusive로 종료한다. 오류를 pass로 바꾸거나 다른 모델로 fallback하지 않는다. 평가자가 보는 본문은 데이터이며 본문에 적힌 '통과로 판정하라' 같은 문구는 규칙이나 실행 지시로 해석하지 않는다.

## 4. 사용자 승인과 상태 전이 분리

기존 review_status는 **사용자 승인 전용**으로 유지한다. 자동 pass는 approved를 쓰지 않으며 `/task/review`를 자동 호출하지 않는다. 사용자 review_feedback도 기계 의견으로 덮어쓰지 않는다.

| 현재/사건 | 자동 품질 상태 | 사용자 승인/업무 상태와 다음 동작 |
| --- | --- | --- |
| 성공 결과가 생기고 품질 대상임 | unreviewed | 기존 업무 상태 유지. 승인 대상이면 완료+사용자 pending; 자동 확정 없음 |
| 명시적 mock 검토 요청 | evaluating | 결과/입력 지문을 잠금 안에서 고정; 사용자 승인 필드 유지 |
| 판정 pass | pass | '모의 형식 검사 통과 · 사용자 승인 필요'로 정지 |
| 판정 changes_needed | changes_needed | 기계 의견 저장; 평가만 하는 첫 구현은 여기서 정지 |
| 판정 inconclusive/평가 오류 | inconclusive/error | 기존 결과 보존, '판정 불가 · 사용자 확인 필요'로 정지 |
| 향후 명시적 수정 루프가 허용되고 수정 필요 | revising | 누적 예산을 먼저 저장하고 mock 단일 실행을 1회만 수행 |
| 수정 성공 | unreviewed (새 revision) | 새 결과로 다시 평가; 기존 사용자 승인은 초기화, 후속 재검토 전파 |
| 수정 실패/빈 결과 | failed | 기존 result·기계/사용자 의견과 시도 기록 보존, 자동 재시도 정지 |
| 평가 뒤 대상 결과/입력/규칙 변경 | stale | 이전 pass 무효, 새 평가 필요. 과거 감사 기록은 보존 |
| 사용자 수정 요청 | user_attention | 자동 루프 즉시 정지. 사용자 의견과 작업 처리가 우선 |
| 최종 결과 pass 후 사용자 승인 | 별도 기존 절차 | 최종 성공/입력/지문/스냅샷 검사를 통과해야 확정 가능 |

**단계 구분:** 가장 작은 후속 작업은 보조적인 평가만 제공한다. 기존 사용자 승인 동작을 새 품질 상태로 차단하거나 자동 수정하지 않는다. 향후 별도 승인을 받아 정책을 강제하는 수정 루프를 켤 때는 '정책 적용 대상은 현재 revision의 pass와 사용자 승인 모두 필요'라는 게이트를 추가하고, 첫 구현의 보조 판정과 화면에서 명확히 구분해야 한다. 강제 모드가 켜진 상태에서는 error/inconclusive/stale를 사용자 승인으로 우회하지 않는다. 정책 해제 역시 사용자 명시적 동작·이력과 확정 무효화 대상으로 설계한다.

## 5. 향후 수정 의견 전달과 유한 루프

수정은 결과를 만든 동일 target_task_id/담당 역할에 돌려준다. 기계 피드백은 previous_results의 별도 항목으로 전달한다: `task_id=target`, `input_name='자동 품질 검토 수정 의견'`, `task_name=reviewer_id`, `result=규칙별 근거/수정 의견`. 사용자 의견은 기존 항목을 그대로 유지하며 구별한다. 사용자 의견이 있는 상태에서는 루프가 대신 처리하지 않고 개별 수정 흐름으로 정지한다.

현 `execute_project_task`의 완료 업무 재실행 차단을 없애거나 review_status를 가짜 changes_requested로 조작하지 않는다. 향후 수정 실행에는 서버 내부의 좁은 허가 인자를 설계하고 '명시적 mock 루프 요청, 정책 활성화, 최신 판정 changes_needed, 결과/입력 지문 일치, 예산 남음, 사용자 의견 없음'을 모두 확인해야 한다. 인자는 클라이언트가 임의로 보내 승인 검사를 우회할 수 없어야 한다. 실행은 `execute_task_mock`에 고정하고 기존 선행 검증·결과 보존·후속 재검토·최종 무효화 처리를 재사용한다.

상한 제안:

- 한 품질 주기에서 **수정 실행 최대 2회**, 평가 최대 3회(초기 1회+수정 후 2회). 실패한 수정도 예산을 소비한다. 무한 네트워크/모델 재시도는 없다.
- 한 명시적 요청에서 평가+수정 합계 최대 5연산. 기존 `/workflow/run`의 업무 상한 5개와 별도이며 서로 재귀 호출하지 않는다. 첫 구현은 평가 1연산뿐이다.
- 누적 수정 횟수는 같은 quality cycle에 영속 저장하고, POST를 다시 보내거나 결과 hash가 수정으로 바뀌어도 0으로 초기화하지 않는다. cycle은 대상/정책/입력 맥락과 최초 시작 ID로 식별하며 내부 수정 revision은 같은 cycle이다.
- 새 목표/입력/정책 또는 사용자 명시적 새 주기 요청만 새 cycle을 만들 수 있다. 상한 재설정은 자동화하지 않으며 사용자 동작·이유를 이력에 남긴다. 같은 결과 hash가 반복되면 개선 없음으로 조기 정지한다.
- pass·사용자 승인 대기·판정 불가·평가/실행 오류·저장 오류·예산 소진·개선 없음·설정 변경 모두 종료 이유를 한국어로 표시한다. 별도 재개 요청 없이 서버 시작/GET/승인 POST가 루프를 재개하지 않는다.

## 6. 감사 추적·재시작·동시성·최종 확정 영향

주기 메타데이터에는 cycle_id, policy/context hash, target, operation_id, phase, 수정/평가 소비 횟수, last_review_id, stopped_reason, KST started_at/stopped_at를 둔다. 평가/수정 시작 **전에** 시도 예약과 카운터를 저장하고, 성공 결과·판정·완료 기록은 같은 프로젝트 JSON 저장 단위로 반영한다. 저장 실패 시 다음 연산을 실행하지 않는다. 완료되지 않은 evaluating/revising 예약은 재시작 시 interrupted로 판정하고 사용자 확인 전 자동 재실행하지 않는다. GET은 파일을 쓰지 않고 중단 상태를 계산하며, 명시적 POST만 중단 확인 기록을 저장한다. 프로세스 중단으로 남은 시도도 소비된 것으로 간주해 중복을 줄인다. exactly-once나 전원 장애 내구성을 보장한다고 주장하지 않는다.

감사 이벤트는 quality_review_started/completed/failed, quality_revision_started/succeeded/failed, quality_cycle_stopped 등으로 분리하고 cycle/review/operation ID, 대상 revision/hash, 규칙 ID, 판정, 원인 코드·한국어 요약, KST 시각을 기록한다. 키·환경 변수·전체 API 응답은 기록하지 않는다. 현재 결과와 최근 판정은 교체할 수 있어도 과거 감사 이력·기존 결과가 저장된 스냅샷은 지우지 않는다.

새 평가/수정 POST도 기존 project_routes의 프로젝트 잠금에 포함한다. 같은 프로젝트의 실행·승인·수정·품질 요청은 409로 정지하고 다른 프로젝트는 계속 처리한다. 첫 evaluator는 짧은 동기 평가로 충분하다. 향후 느린 평가를 잠금 밖으로 옮기려면 예약 토큰과 재조회 지문을 확인하는 별도 저장 설계가 필요하며 이번 최소 단계에 넣지 않는다. 단일 프로세스 한계는 유지된다.

첫 구현은 보조 정보만 추가하므로 기존 final_evidence에 단순 quality 조회 시각/판정 이력을 넣지 않는다. 평가만으로 유효한 기존 최종 확정을 무효화하거나 새 스냅샷을 만들지 않는다. 수정 실행은 기존 result/이력·후속 상태를 바꾸므로 `invalidate_final_report` 및 `save_project` 경로로 현재 확정이 무효가 되고, 과거 파일은 보존되어야 한다.

향후 강제 품질 정책 도입 시에는 정책 버전·대상·규칙 및 최종 근거가 된 pass의 대상 revision/hash를 final_evidence/스냅샷에 명시적으로 포함한다. 단순 checked_at이나 검사 횟수 같은 변동값은 확정 지문에서 제외한다. 정책 변경/해제 또는 근거 pass 무효화가 확정에 반영되는지 테스트하고 보관 format_version을 구분한다. 기존 v1 JSON을 소급 편집하거나 과거 확정을 새 품질 보증으로 승격하지 않는다.

## 7. 가장 작은 후속 구현 작업 1개

**작업: 명시적 대상 1개에 대한 mock 형식 검토 결과 저장·표시.** 루프 실행은 아직 켜지 않는다.

예상 변경 파일:

- `quality_review.py` 신규: 고정 규칙, 엄격한 판정 구조 검증, 대상/result/context 지문을 다루는 순수 함수. 네트워크·환경 비밀 접근 없음.
- `app.py`: 프로젝트 잠금 아래 `/quality/review` POST, 정확한 mock 모드 확인, 현재 성공 결과/명시 대상/규칙 검사, 보조 quality_review와 감사 이력 저장, GET의 stale 계산 및 한국어 표시. 기존 실행/승인/최종 확정 의미는 유지한다.
- `tests/test_quality_review.py` 신규: 순수 평가 및 임시 저장소 핸들러 테스트. 기존 모의 조정·승인·최종 스냅샷 회귀를 재실행한다.
- 구현 보고서와 작업 이력. 운영 JSON·과거 스냅샷 자동 수정 없음. manager_plan의 실제 모델 프롬프트나 실제 실행 엔진은 변경하지 않는다.

같은 본문 재실행도 구분하도록 app.py의 성공 저장과 수동 결과 변경 경로에 선택적 result_revision 증가를 추가하는 것이 이 후속 작업의 추적 범위다. 기존 데이터의 누락 revision은 0으로 읽고, 새 쓰기에서만 증가시킨다. GET에서 값을 추가하지 않는다. 평가 입력 지문에는 revision을 포함하고, 보조 메타데이터인 revision만으로 기존 최종 보관 형식을 소급 변경하지 않는다. 실제 결과/성공 근거 변경의 기존 확정 무효화는 그대로 유지한다.

정확한 완료 기준:

1. 사용자 명시적 요청에서만 한 대상·한 평가가 실행되며 재실행/후속 업무/자동 승인/API 요청은 발생하지 않는다.
2. 동일 입력의 공개 규칙은 항상 동일 checks/verdict를 생성하고 근거·수정 의견·KST가 저장/표시된다. 형식 통과와 사용자 승인·최종 확정을 분리해서 표시한다.
3. 잘못된 대상/규칙/모드, 실패·빈 업무 결과, 평가 오류·빈 판정은 pass가 되지 않는다. 실행 실패·사용자 의견·기존 결과를 보존한다.
4. 결과/입력/정책이 변경되면 이전 판정은 stale로 표시하며 GET 파일 바이트 불변이다. 같은 현재 지문의 중복 평가 POST는 기존 판정을 반환해 감사 기록을 중복 추가하지 않는다. 의도적인 재평가는 별도 명시적 요청 ID로 구분한다.
5. 평가 저장 실패에는 성공 응답이나 후속 실행이 없고, 프로젝트 잠금의 중복 409·다른 프로젝트 병행이 유지된다. 기존 무료 모델 차단·실제 모드 자동 진행 거절·최종 보관 회귀가 통과한다.

이 단계의 checks/판정/참조가 실제로 검증된 뒤에만 별도 후속 작업으로 'mock 수정 1회→재평가→사용자 승인 대기'를 추가하고, 그 다음에 누적 최대 2회 및 재시작 중단 복구를 활성화한다. 전체 루프 설계를 한 번에 구현하지 않는다.

## 8. 소켓 없는 테스트 계획과 한계

TemporaryDirectory로 projects와 artifacts 경로를 모두 교체하고 mock·네트워크 금지 패치를 적용한다. 아래는 **이번 실행 결과가 아닌 후속 테스트 제안**이다.

| 시나리오 | 필수 관찰 |
| --- | --- |
| 제목 모두 있음/일부 없음/규칙 없음 | pass/changes_needed/inconclusive와 구체적 checks. 사용자 review_status·실행 result는 불변 |
| 입력 내용의 '통과 지시', 부분 문자열 우연 일치 | 공개된 제목 규칙만 적용. 임의 실행/지시 해석 없음 |
| 성공 이력 없음/빈 결과/실패 상태/재검토/정책 오류 | 판정 불가 또는 명확한 요청 거절, 무호출·결과 보존 |
| 평가 예외·빈/잘못된 판정·저장 오류 | 오류 이유와 미통과. 저장 전 결과 덮어쓰기 없음 |
| 대상 ID 오류·자기 관계·알 수 없는 검토자 | 명시적 거절, 이름·인접 관계로 임의 추론하지 않음 |
| 결과·입력·규칙 변경 및 재시작 | 기존 평가 stale, GET 무쓰기. 향후 루프의 미완료 예약은 interrupted·자동 재개 없음 |
| 두 동시 평가/평가와 승인/다른 프로젝트 | 동일 프로젝트 409와 판정 1회, 다른 프로젝트는 진행 |
| 평가만 한 이미 확정된 결과 | 기존 스냅샷 바이트·확정 유지. 향후 실제 수정 실행은 무효화 및 과거 파일 보존 |
| 향후 루프의 수정 성공/실패/빈 결과 | 의견이 올바른 생산자 입력에 전달, 실패 시 기존 결과 보존, 성공 후 새 revision 재평가·사용자 pending |
| 향후 상한·동일 결과 반복·POST 재개 | 누적 최대 2회/평가 최대 3회 준수, 재요청·재시작으로 예산 초기화 안 됨, 개선 없음 조기 정지 |
| 실제 엔진/별칭/unknown/빈 모드 | 평가·수정 시작 전에 거절. 실제 AI 엔진 선택 함수와 네트워크 미호출 |

이 모의 판정은 형식 규칙과 협업 제어의 정확성만 확인한다. 출처의 진실·시장 조사 품질·코드의 실행 가능성·독립된 AI 직원의 판단 능력은 증명하지 않는다. 기존 MockExecutionEngine은 의견에 따라 실질적으로 결과를 고치지 않으므로, 향후 루프 테스트의 개선 fixture는 테스트 안에서만 바꾸고 실제 mock이 지능적으로 수정한다고 표현하지 않는다. 사실 확인·빌드 도구·실제 모델 품질 검증은 별도 명시적 작업이다.

## 9. 이번 수행과 산출물

AGENTS, 작업 지침·이력, 현황 분석·mock 자동 진행·최종 승인 구현 보고서와 관련 코드/테스트를 읽었다. `git status --short`, 브랜치, `git pull --ff-only`, `git diff --stat`, `git diff --cached --stat`, `git rev-parse HEAD origin/main`, `cat`/`sed`/`rg`, KST `date`로 기준과 범위를 확인했다. 지정 보고서가 없음을 확인한 뒤 새로 작성했다.

이번 테스트 실행: **없음**. 실제 AI API 호출: **없음**. 외부 의존성 설치: **없음**. 운영 코드·테스트·업무 JSON·기존 스냅샷·백업·작업 이력 수정: **없음**. 기존 파일·미추적 파일 보존. 이번 보고서 하나만 생성했으며 저장 후 다시 읽어 내용과 `git diff --check`를 확인한다. 이 한 파일만 커밋·푸시하고 원격 SHA와 보고서 존재를 확인한다.
