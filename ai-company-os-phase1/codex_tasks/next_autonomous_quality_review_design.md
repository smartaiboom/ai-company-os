# 다음 작업: AI 직원 간 자율 품질 검토·수정 루프 설계

## 목적
AI Company OS의 핵심 목표는 사용자가 목표를 주면 AI 직원들이 계획, 업무 수행, 결과 전달, 상호 검토, 수정, 최종 보고까지 협업하는 가상회사를 만드는 것이다. 현재 mock 업무 자동 진행, 사용자 검토 승인, 최종 보고서 확정까지 구현됐지만 직원 간 자동 품질 판정과 피드백·수정 루프는 없다. 이번에는 **실제 API 없이 안전하고 작은 자율 품질 검토 흐름을 구현할 수 있도록 설계만 수행한다.**

- 실제 AI API 호출 금지, 외부 의존성 설치 금지, 운영 코드 및 테스트 수정 금지.

## 분석·설계 질문
1. 현재 직원 역할과 선행 결과 전달의 구조를 바탕으로 누가 누구의 결과를 검토할지 결정하는 최소한의 명시적 규칙을 제안한다. 기존 사용자 승인 게이트와 자동 품질 평가를 별개로 구별한다.
2. 자동 검토 결과를 통과/수정 필요/판정 불가로 구조화하고, 판단 근거와 수정 의견을 저장하며, 실패하거나 빈 결과인 경우를 안전하게 처리하는 상태 전이를 설계한다.
3. 첫 구현은 mock만 사용하고, 결정론적 테스트가 가능한 판정 기준으로 한정한다. 실제 모델 자동 호출은 절대로 활성화하지 않는다.
4. 수정 의견을 기존 업무 실행 입력으로 돌려보내는 방법, 직원 간 결과 변경 전파, 승인 대기와 사용자 개입 지점을 명확히 한다.
5. 끝없는 수정 루프를 막는 최대 재시도 횟수, 사용자에게 정지 이유 설명, 이력·감사 추적, 재시작 시 상태 판정, 오류 시 기존 결과 보존을 제안한다.
6. 동시 실행 보호와 최종 확정 무효화/스냅샷 보관에 어떤 영향이 있는지 확인한다.
7. 구현을 한 번에 크게 하지 말고 가장 작은 구현 작업 1개와 완료 기준, TemporaryDirectory 및 mock을 이용한 테스트 시나리오를 제안한다. 실제 결과 품질과 mock의 검증 한계를 명확히 구분한다.

## 필수 결과 파일
- 보고서는 반드시 reports/autonomous_quality_review_design_20261102.md 에 작성한다. 기존 파일이 있으면 먼저 읽어 보존하고 임의 덮어쓰기 금지.
- 현재 코드 근거, 선택한 설계, 대안·위험, 상태 전이, 데이터/화면 변화, 예상 변경 파일, 테스트 계획, 구현 완료 기준, 실제 API 호출 여부를 포함하고 저장 후 재독한다.
- 이번 분석 보고서 **한 파일만** 안전하게 스테이징·커밋하여 origin/main에 푸시한다. 다른 미추적 파일과 사용자 변경은 포함하지 않는다. 충돌 시 푸시 중단. 원격 보고서와 커밋 SHA 확인.
- 결과를 대화에만 남기지 않는다. 완료 보고는 파일 경로·커밋 SHA·푸시 결과를 간단히 적는다.
