# mock 품질 형식 검토 저장·표시 구현

작성: 2026-11-02 12:19 KST
기준: `1ec3a199a9a86351bbb93050a657afd49e7a5e73` main/origin/main 동기화 후 작업

## 실제 구현 범위

- `quality_review.py`: 파일·환경·AI·네트워크에 접근하지 않는 순수 모듈이다. 고정 검토자 `mock-quality-reviewer-v1`, 공개 규칙 `required-sections-v1`로 '목표', '결과', '미확인 사항'이 독립된 줄 또는 1~6단계 Markdown 제목으로 있는지 검사한다. 코드 펜스 안의 예시 제목, 인용/목록, 부분 문자열, 본문의 '통과하라' 지시는 제목으로 인정하지 않는다.
- `evaluate_format`은 pass/changes_needed/inconclusive와 규칙별 기대 제목·충족 여부·행 번호, 한국어 피드백을 반환한다. 빈/잘못된 입력과 알 수 없는 규칙·검토자는 판정 불가다. `validate_review`는 판정 enum·고정 정책·피드백 형식·3개 검사 근거와 pass의 일관성을 검증한다.
- `app.py:/quality/review`: 정확한 업무 ID 하나와 고정 규칙/검토자를 받는 명시적 POST다. 기존 프로젝트 잠금에 포함하며 mock 외 모드·잘못된 ID/규칙·검토자를 거절한다. 완료·비공백 결과·최신 성공 이력·재검토 해제·필수 선행 승인을 검사한다. 새 실행 결과는 실행 당시 맥락과 현재 맥락이 다르면 검사를 거절한다.
- `result_revision`은 구형 누락을 0으로 읽는다. 성공 실행 시(동일 본문이라도) 증가하고 수동 결과 변경에도 증가한다. 새 실행에는 quality_execution_context를 저장한다. 조회만으로 이 필드를 추가하거나 기존 JSON을 변환하지 않는다.
- `quality_binding`은 대상 ID, result revision/hash, 입력 맥락 지문, 규칙/검토자 정책 지문을 묶는다. quality_review에 이 binding, 구조화 판정, 결과 상태(outcome), review_id, checked_at(KST)를 저장하고 품질 검토 감사 이벤트를 추가한다. 동일 binding의 유효한 기존 판정은 추가 평가·저장·이력 없이 재사용한다.
- 평가 예외나 잘못된 응답은 오류 내용을 그대로 노출하지 않고 outcome=error/verdict=inconclusive로 저장한다. 오류를 통과로 바꾸지 않는다. 프로젝트 저장 실패에는 오류 응답을 반환하고 저장된 원본은 유지한다.
- 검증 중 발견한 기존 응답/잠금 경합도 최소 수정했다. 저장·판정이 완료된 요청은 응답 전 잠금을 해제하고 finally는 아직 소유한 잠금만 해제한다. 따라서 응답 직후 정상적인 다음 요청이 이전 잠금 때문에 409를 받지 않는다. 실제 평가·실행 중의 409 보호는 유지한다. 입력 버전·맥락 오류도 실행기를 부르기 전에 검사해 기존 결과를 보존한다.
- 업무별 UI에는 '모의 형식 검사', 공개 규칙·사실성 검증이 아니라는 설명, 판정·누락 항목·행 근거·수정 의견·KST 검사 시각, mock 전용 명시적 검사 버튼을 표시한다. 현재 결과·입력·정책 binding과 다르거나 선행 검증이 불가능하면 stale(이전 판정)로 표시한다. GET은 계산만 하며 JSON을 쓰지 않는다.

보조 판정은 review_status, 사용자 수정 의견, 업무 result, 실행/승인 게이트, 최종 확정 참조를 변경하지 않는다. final_evidence에 품질 메타데이터를 넣지 않았으며 평가만으로 기존 스냅샷을 재작성·무효화하지 않는다. 결과 재실행·후속 자동 실행·자동 승인·자동 수정 루프는 구현하지 않았다. 실제 AI 엔진과 `openrouter/free` 제한은 변경하지 않았다.

## 변경 파일

1. `quality_review.py`: 순수 평가·판정 검증 모듈 신규.
2. `app.py`: mock 평가 POST·잠금·입력/결과 추적·업무별 표시 및 결과 revision.
3. `tests/test_quality_review.py`: 신규 15개 테스트(순수 평가 4개, 격리 통합 11개).
4. `codex_tasks/task_history.md`: 결과 이력.
5. `reports/mock_quality_review_implementation_20261102.md`: 이 보고서.

기존 업무 JSON·결과·스냅샷·백업·무관한 미추적 파일을 수정·삭제·스테이징하지 않았다. 운영 데이터 자동 변환·외부 의존성 설치 없음.

중간 전체 실행은 101개 중 100개 통과/1개 skip이었다. 입력 버전 회귀 추가 뒤 102개 실행에서는 기존 HTTP 테스트가 이전 응답 직후 400 대신 409를 받아 1개 실패했다. 저장 완료 후 응답 전에 잠금을 해제하도록 수정해 102개 중 101개 통과/1개 skip을 확인했고, 이 타이밍을 직접 재현하는 회귀 테스트를 추가한 최종 103개 실행도 통과했다. 실패를 단순 재시도로 무시하지 않고 경합 원인을 수정했다.

신규 검증은 제목 충족/누락·입력/규칙 오류·프롬프트형 지시 무시, 모드/대상/완료/재검토/입력 맥락 검사, 잘못된 평가/예외의 판정 불가, 중복 멱등성, 결과·입력·정책 변경 stale, GET 파일·메모리 무변경, 사용자 수정 의견 유지, 확정 스냅샷 바이트·참조·유효성 유지, 저장 실패 시 400/원본 보존, 같은 본문 재실행 revision 증가, 평가와 승인/실행 경쟁 409 및 다른 프로젝트 병행을 확인했다.

저장은 TemporaryDirectory의 projects/artifacts로 교체했다. 실행기는 mock, 실행/계획 네트워크 함수는 호출 금지 mock이다. 신규 테스트는 소켓 없이 실제 POST 핸들러를 직접 호출하고 동시성은 Event/ThreadPoolExecutor로 확인했다. 전체 실행은 승인된 환경에서 기존 임시 loopback 서버만 사용했다. 실제 AI API 호출: **없음**. 실제 비밀 키·환경 설정 파일 접근: **없음**. 유료 서비스·의존성 설치: **없음**.

`git diff --check` 통과. 지정 보고서가 없음을 확인한 뒤 신규 작성하고 보고서 및 작업 이력을 재독했다. 관련 파일만 스테이징 후 staged diff를 확인한다.

## 제한과 남은 위험

- 통과는 제목 존재에 대한 형식 검사뿐이다. 제목 아래 내용의 충실성, 사실성, 출처·코드 품질은 검증하지 않는다. 고정 문구를 내는 기존 mock이 지능적으로 수정한다고 주장하지 않는다.
- 품질 검토가 보조 정보이므로 changes_needed/inconclusive가 기존 사용자 승인을 새로 차단하지 않는다. 사용자 승인·최종 확정은 기존 조건으로 판단한다. 강제 품질 게이트와 유한 수정 루프는 후속 단계다.
- 새 실행의 입력 맥락은 지문으로 비교한다. 구형 성공 결과에 quality_execution_context가 없으면 현재 선행 검증과 현재 맥락으로 평가하며, 과거 실행 당시 실제 입력을 복원했다고 주장하지 않는다. 구형 결과를 새로 실행하면 맥락과 revision이 기록된다.
- 입력 지문은 모든 앞선 업무의 근거를 보수적으로 포함하므로 직접 의존하지 않는 이전 업무 변경에도 stale가 될 수 있다. 검토 대상 자신의 사용자 승인·수정 의견은 별도 상태이며 형식 검사만으로 변경하지 않는다.
- 오류/판정 불가도 현재 binding에 대한 판정으로 저장되어 같은 입력의 중복 요청은 재사용한다. 강제 재평가용 별도 요청 ID UI는 이번에 구현하지 않았다. 결과·입력 변경 뒤 새 binding은 다시 검사한다.
- 프로젝트 잠금은 동일 프로세스 앱 POST 경로만 보호한다. 다중 프로세스·외부 파일 편집·재시작 복구와 장시간 백그라운드 처리는 새로 구현하지 않았다.
- 실제 브라우저 버튼·모달·화면 배치를 실행하지 않았다. 렌더링 HTML과 직접 핸들러·기존 HTTP 회귀만 검증했다. 실제 AI 모델은 호출·검증하지 않았다.

다음 단계는 이 보조 평가의 격리된 HTTP/브라우저 검증, 이후 별도 지시 아래 mock 수정 1회→재평가→사용자 승인 대기다. 이번 구현은 기존 자동 진행에 품질 루프를 자동 삽입하지 않는다.

관련 5개 파일만 커밋·푸시하고 원격 커밋과 보고서 존재를 확인한다. 테스트가 생성한 스냅샷이나 기존 업무 데이터를 Git에 포함하지 않는다.
