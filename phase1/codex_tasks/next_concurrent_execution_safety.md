# 다음 작업: AI 직원 업무 중복 실행과 동시 저장 안전성 개선

## 목적
AI Company OS가 미래에 AI 직원 업무를 자동으로 연결 실행하기 전에, 같은 업무에 대한 중복 HTTP 요청과 저장 충돌로 결과가 덮어써질 수 있는 위험을 최소 범위에서 막는다. 가상회사 전체 목표와 기존 검토 승인 게이트를 유지한다.

## 선행 확인
1. `AGENTS.md`, `codex_tasks/README.md`, `reports/ai_company_os_current_state_audit_20261102.md`, `reports/execution_mode_notice_fix_20261102.md`를 읽는다.
2. `app.py`의 `ThreadingHTTPServer`, 프로젝트 읽기/쓰기, `/task/execute`, `/task/review`, 관련 상태 변경 흐름과 테스트를 확인한다.
3. 현재 브랜치·origin/main·git status/diff를 확인한다. 기존 변경, 미추적 파일, 프로젝트 JSON, 결과, 백업을 절대로 삭제·초기화·강제 덮어쓰기 하지 않는다. KST로 기록한다.

## 구현 범위
- 먼저 동시 요청의 실제 위험을 코드와 격리된 재현 테스트로 확인한다. 문제가 재현되지 않거나 안전한 최소 수정이 어렵다면 무리하게 바꾸지 말고 분석 보고서에 이유를 남긴다.
- 동일 프로젝트/업무에 대한 중복 실행 요청이 동시에 들어왔을 때 둘 다 AI 실행을 시작하지 않도록 서버 측 안전 장치를 최소한으로 구현한다. 브라우저 JS만으로 차단하는 것은 부족하다.
- 검토 승인·수정 요청과 실행 간 저장/상태 변경 경합에 대해서도 점검한다. 필요한 최소 범위에서 상태 판정과 저장을 일관되게 보호한다.
- 기존 단일 요청의 상태 전이, 이전 결과 보존, 승인 전 후속 전달 금지, 실패/빈 응답 처리, `openrouter/free` 제한은 그대로 유지한다.
- 사용자 데이터 파일 구조와 기존 API 사용 방식은 불필요하게 변경하지 않는다. 동시성 보호의 범위(동일 프로세스/여러 프로세스/재시작 후)를 정확하게 명시한다. 테스트에서 안전하다고 증명하지 않은 범위를 보호한다고 주장하지 않는다.
- 기존 실행이 오래 걸리는 동안 전체 서버를 불필요하게 막지 않도록 잠금 범위와 UX를 검토한다.

## 검증·안전
- 네트워크와 실제 AI API는 호출하지 않는다. 지연 또는 카운팅 mock 실행기와 임시 프로젝트 저장 폴더를 사용한다.
- 가능한 경우 2개 동시 요청, 승인/실행 경쟁, 오류 발생 후 재시도, 서로 다른 업무 요청을 격리 테스트한다. 실제 데이터 경로를 사용할 위험이 있는 테스트는 실행하지 않는다.
- 변경 관련 unittest와 기존 핵심 회귀 테스트를 실행하고 `git diff --check`를 확인한다. 실패 시 커밋/푸시를 중지하고 보고한다.
- 외부 의존성 추가, 대규모 리팩터링, 유료 모델 설정, 실제 API 호출, 기존 파일 삭제/초기화 금지.

## 보고 및 전달 (필수)
- 결과는 반드시 `reports/concurrent_task_execution_safety_20261102.md` 파일로 저장한다. 근거, 실제 변경 내용, 테스트 명령/통과 수, 남은 위험, 데이터 격리 및 AI API 호출 여부를 적고 다시 읽어 검증한다.
- 기존 같은 이름의 파일이 있으면 먼저 읽고 보존하며 덮어쓰지 않는다.
- 의도한 코드/테스트/보고서/필요한 작업 이력 파일만 선택적으로 스테이징하여 main에 안전하게 커밋하고 origin/main에 푸시한다. 미추적 기존 파일은 포함하지 않는다. 원격 충돌이나 테스트 실패가 있으면 푸시하지 않는다. 강제 push 금지.
- 결과를 대화에만 남기지 말고 반드시 보고서 파일과 GitHub 반영을 확인한다. 완료 응답은 결과 파일 경로, 검증 결과, 커밋 SHA/푸시 여부를 간단히 보고한다.
