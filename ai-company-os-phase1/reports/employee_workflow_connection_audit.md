# AI 직원 간 업무 연결 흐름 조사

## 조사 범위와 방법

- `app.py`, `execution_engine.py`, `manager_plan.py`의 계획 승인·업무 실행·입력 전달·결과 저장 흐름을 읽었다.
- 관련 모의 테스트인 통합 업무 흐름, 검토 수정 흐름, 실행 저장·실패 차단, 후속 재검토 테스트를 확인하고 실행했다.
- 기능 코드, 기존 프로젝트 데이터, 업무 결과, 백업 파일은 변경하지 않았다. 실제 AI API 호출도 하지 않았다.

## 실행 흐름

1. `/manager/plan`은 `build_manager_plan()`으로 계획을 만든다. 기본 `mock` 모드에서는 시장 조사·제품 기획·개발 계획이 아니라 `요구사항 정리 → 작업 초안 작성 → 검토 및 수정 → 최종 보고` 네 단계의 공통 계획을 사용한다. AI 계획 모드에서는 응답의 각 단계에 `name`, `role`, `inputs`, `output`, `risk`가 있는지 검사한다.
2. 사용자가 계획을 승인하면 각 계획 단계가 작업으로 복사된다. `inputs`와 `output`은 작업 데이터에 보존된다.
3. `/task/execute`는 현재 작업보다 앞선 작업이 모두 `완료`이고 재검토 표시가 없어야 실행을 허용한다. 완료한 선행 작업 중 결과가 있는 항목을 모은 다음, 현재 작업의 각 `inputs` 문구와 선행 작업의 이름·산출물을 정확 일치 또는 부분 문자열로 비교한다.
4. 일치한 결과는 `previous_results`로 `execute_task()`에 전달된다. 모의 엔진은 결과 텍스트에 연결 자료를 넣고, AI 호환 엔진은 해당 목록을 요청 본문에 넣는다. 실행 결과가 비어 있으면 실패 처리하고 저장하지 않는다. 성공하면 결과와 완료 상태를 저장한다.

## 질문별 확인 결과

### 시장 조사 → 제품 기획

- **확인된 사실:** 후속 전달 구조는 있다. 선행 업무의 `result`를 입력 목록과 매칭해 넘길 수 있으며, 제품 기획 입력이 시장 조사 작업의 이름 또는 산출물과 맞으면 실제 전달 대상이 된다.
- **저장 데이터 확인:** 프로젝트 식별자와 결과 본문은 보고서에 노출하지 않고 작업 메타데이터만 읽었다. 저장된 프로젝트 중 `시장 조사 → 제품 기획 → 개발` 계획 하나를 확인했다. 세 업무 모두 `완료`, 결과 있음, 재검토 표시 없음이며, 제품 기획의 `시장 조사 보고서` 입력은 시장 조사 산출물과 문자열로 매칭된다.
- **실제 전달의 증거 범위:** 저장 상태와 현재 코드의 매칭 규칙을 대조하면 이 프로젝트 흐름은 실행 당시 전달 조건을 충족한다. 다만 실행 시점의 `previous_results` 요청 내용은 기록되지 않으므로, 과거 호출에 포함된 본문을 사후 로그로 직접 확인한 것은 아니다.
- **확인된 한계:** 기본 모의 계획에는 시장 조사와 제품 기획 단계가 없다. 테스트의 통합 흐름도 기본 네 단계 계획을 대상으로 한다. 따라서 이 특정 연결을 고정적으로 검증하는 회귀 테스트는 없다.
- **확인된 위험:** 입력 이름이 선행 작업명·산출물과 매칭되지 않으면 입력이 전달되지 않아도 실행 자체는 계속된다. 계획에 연결이 적혀 있어도 결과 전달이 보장되지는 않는다.

### 제품 기획 → 개발

- **확인된 사실:** 같은 `inputs` 매칭과 `previous_results` 전달 구조를 이용하면 제품 기획 결과를 개발 업무에 전달할 수 있다. AI 실행 요청에는 작업의 필요 입력과 이전 결과가 함께 포함된다.
- **저장 데이터 확인:** 위 프로젝트에서 개발의 `제품 기획서` 입력은 제품 기획 산출물과 매칭되며, 개발도 완료 상태와 비어 있지 않은 결과를 가지고 있다. 실행 당시 페이로드가 저장되지 않아 과거에 실제 전달된 본문을 직접 확인할 수는 없다.
- **확인된 한계:** 기본 모의 계획 및 통합 테스트에는 제품 기획 담당 업무 다음에 개발 담당 업무가 실행되는 사례가 없다. 저장 데이터에서는 연결 조건이 충족되지만 이 특정 경로의 회귀 테스트는 없다.

### 선행 실패 또는 빈 결과

- **확인된 사실:** 앞선 작업이 실패·진행 중·대기·재검토 상태이면 이후 작업 실행은 차단된다. 테스트는 실패한 선행 업무 뒤에서 `execute_task()`가 호출되지 않고 후속 작업이 대기 상태로 남는 것을 확인한다.
- **확인된 사실:** 현재 실행이 빈 문자열을 반환하면 실패로 처리하고 그 빈 결과를 저장하지 않는다. 일반적인 상태 저장 경로도 결과가 비어 있으면 완료 상태로 바꾸지 못하게 한다.
- **주의할 예외:** 실행 전 차단 조건은 선행 작업의 상태를 확인하지만 모든 완료 작업의 결과가 공백이 아닌지 별도로 검사하지는 않는다. 정상 UI 경로에서는 빈 결과의 완료 저장이 거부되지만, 기존 데이터나 외부에서 만들어진 `완료 + 빈 결과` 레코드까지 실행 경로가 막는지는 보장되지 않는다. 또한 입력 매칭 실패는 오류가 아니라 전달 자료 없음으로 취급된다.

### 검토와 수정

- **확인된 사실:** 품질 검토 역할과 검토 업무가 있고, 선행 결과가 바뀌면 이미 진행 중이거나 완료된 후속 작업을 `재검토 필요`로 표시한다. 해당 작업은 상태만 완료로 바꿀 수 없고 다시 실행해야 한다. 통합 테스트와 검토 흐름 테스트는 초안 변경 후 검토·최종 보고를 재실행해 새 결과를 반영하는 과정을 확인한다.
- **확인된 한계:** 검토 결과에 합격/불합격을 판정해 다음 단계 실행을 자동 허용·차단하는 품질 게이트는 확인되지 않았다. 검토 의견에 대한 사람의 승인이나 수정 요청은 작업 결과 전용 절차로 구현되어 있지 않다. `/manager/reject`는 작업 계획 수정 요청 기능이다. 따라서 검토 업무를 실행하고 재검토하는 흐름은 있지만, 승인된 검토 완료를 보장하는 절차는 부분 구현이다.

## 독립 실행과 결과 연결의 구분

- 앞선 모든 작업이 완료 상태면 순서상 다음 작업을 실행할 수 있다. 그러나 현재 작업의 `inputs`가 비어 있거나 어떤 선행 작업과도 매칭되지 않으면 `previous_results` 없이도 실행할 수 있다. 즉 순서 게이트와 자료 전달은 별도이며, 순서가 지켜졌다고 결과가 연결된 것은 아니다.
- 입력 매칭은 명시적 작업 ID 대신 이름·산출물의 문자열 포함 여부에 의존한다. 비슷한 문자열이 여러 작업과 맞으면 여러 결과가 전달될 수도 있다.
- 작업 순서는 입력 연결 여부와 무관하게 모든 이전 작업의 완료를 요구하는 직렬 방식이다. 서로 의존하지 않는 업무도 앞 작업이 끝나기 전에는 실행할 수 없다.
- 모의 엔진은 외부 조사를 수행하지 않았다고 결과에 명시한다. AI 실행 프롬프트도 출처 없는 사실을 만들지 말고 미검증 주장을 구분하라고 지시하지만, 이번 코드 범위에서 시장 데이터 수집·출처 확인을 수행하는 별도 검색 연결은 확인되지 않았다.

## 테스트 근거

- `tests/test_company_workflow_e2e.py`: 기본 계획 승인부터 작업 실행, 검토 결과 변경 후 후속 검토 재실행 및 최종 보고까지 확인한다. 테스트에서 계획기·실행기 네트워크 호출은 차단한다.
- `tests/test_task_execution_persistence.py`: 실행 실패와 빈 결과 저장 방지, 실패한 선행 업무의 후속 실행 차단을 확인한다.
- `tests/test_quality_review_flow.py`: 선행 결과 변경 시 후속 검토 표시, 상태만 완료로 바꾸는 우회 차단, 재검토 및 최종 업무 재실행을 확인한다.
- `tests/test_downstream_review.py`: 대기 작업은 대기 상태로 두고 이미 진행/완료된 작업만 재검토 대상으로 표시하는 규칙을 확인한다.
- 명령: `python -B -m unittest tests.test_company_workflow_e2e tests.test_quality_review_flow tests.test_task_execution_persistence tests.test_downstream_review`
- 결과: 10개 테스트 통과 (`OK`). 테스트는 임시 프로젝트 디렉터리와 모의 실행 경로를 사용했다.

## 미확인 사항

- 저장된 프로젝트 하나에서 목표 업무 단계, 입력·산출물 이름, 완료 상태와 결과 존재 여부를 읽어 확인했다. 기존 결과의 본문은 출력하거나 보고서에 복사하지 않았다.
- 해당 프로젝트의 과거 실행 요청 페이로드에 `previous_results`가 실제 어떤 본문으로 담겼는지는 별도 기록이 없어 직접 확인할 수 없다.
- 정확한 3단계 계획의 전달을 검증하는 통합 테스트는 없다.
- AI API는 호출하지 않았으므로 실제 제공자 응답 품질, 생성 결과에서 입력 자료를 정확히 활용하는지는 검증되지 않았다.

## 개선 우선순위

1. **필수 — 입력 연결을 명시적으로 검증:** 입력을 문자열 유사도로 찾는 대신 선행 작업 ID나 산출물 ID로 연결하고, 필수 입력을 찾지 못했거나 결과가 비어 있으면 실행을 막고 어떤 연결이 빠졌는지 보여준다. 완료 상태인 선행 작업의 결과 비어 있음도 실행 전 검사한다.
2. **필수 — 목표 업무 흐름 회귀 테스트:** 시장 조사 결과가 제품 기획 입력에 들어가고, 제품 기획 결과가 개발 입력에 들어가는 3단계 모의 통합 테스트를 추가한다. 실제 API 없이 전달 내용과 실패·빈 결과 차단을 검증한다.
3. **다음 단계 — 검토 승인 게이트:** 합격 기준, 검토 통과/수정 요청 판정, 수정 의견 반영, 재검토 통과 전 최종 업무 차단을 데이터와 UI에서 명확히 구분한다.
4. **다음 단계 — 독립 업무 구분 및 증거 연결:** 선행 입력이 없는 업무는 독립 작업으로 표시하고 병렬 실행 가능성을 검토한다. 시장 조사 결과에는 출처·수집 시점·검증 여부를 연결해 AI 생성 주장과 확인된 근거를 구분한다.

- 기능 코드와 프로젝트 데이터 변경: 없음.
- 실제 AI API 호출: 없음.
