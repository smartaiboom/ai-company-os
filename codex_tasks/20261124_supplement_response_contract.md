## 실제 실패 진단
대표가 승인된 관리자 보완 시작을 실행했고 "Gemini 응답 형식이 필요한 구조와 일치하지 않습니다." 표시. 실제 HTTP, 응답 수신, 예약/완료 횟수, 실패 단계는 아직 미확인. 로컬 v6 운영 저장소, supplement-step별 계약/시도/응답 진단, 서명 및 업무 원장을 읽기 전용으로 확인한다. 실제 응답이 보존되어 있으면 안전한 로컬 복제본에서 파싱/검증 실패 필드와 원인을 재현한다. 미보존 원문은 추정하지 않는다. 원문이나 키를 GitHub에 올리지 않는다.

## 수정 및 검증
- companies/video/research_supplement.py의 model(), SupplementWorker, task_replanning schema/validate, role_json_schema, ProductionManager 및 공통 Gemini 응답 처리 경로를 추적. 특히 최초 관리자 지시의 wire_schema와 로컬 plan_contract, 직원 도구 선택/최종 보고 및 관리자 검토 계약의 일치 여부를 실제 실패 증거로 확인한다. HTTP 성공 후 파싱 실패/스키마 불일치/업무 규칙 위반을 분리한다.
- 실제 확인된 결함을 수정하고 관련 단계 전체를 통합 검증한다. 표현 차이, 안전하게 정규화 가능한 형식과 실제 의미/권한/근거 위반을 구분한다. 단순 형식 차이는 의미를 바꾸지 않는 결정적 로컬 정규화와 재검증을 우선 고려한다. 근거/권한/출처 검증을 제거하거나 AI 판단을 개발자가 대신 생성하지 않는다.
- 기존 승인 범위와 원장을 보존한다. 이미 수신된 유효 결과 및 성공 조사 자료를 재사용하고, 필요한 경우 확인된 계약 수정에 근거한 새 서명/예약 및 승인된 잔여 업무 예산으로 미완료 단계만 재검증할 수 있는 기존 복구 경로를 검토한다. 기존 실패·미확정 요청 자동 재전송 금지, 승인 확대 필요 시 별도 승인. 원인 미확인이면 보류하고 다음 확인 방법을 제시한다.
- 최신 운영 기준대로 지나치게 엄격한 형식 차단이나 임의의 소량 제한으로 품질을 저해하지 않는다. 정상 추가 조사와 실제 실패를 구분한다. 이번 오류가 한도 때문이라고 단정하거나 관련 없는 예산 시스템을 재설계하지 않는다.
- 먼저 저장 응답/fixture/mock과 운영 복제본으로 관리자 지시→직원 조사→최종 보고→관리자 검토 흐름 및 형식 오류, 의미 위반, 승인·중복 차단을 검증한다. 이후 Codex가 직접 컷룸 서버 및 실제 UI/동일 서비스 경로를 실행하고, 기존 승인이 개발 검증 목적 및 해당 실행의 공급자·모델·프로젝트·전송 데이터·무료 조건·만료·잔여 총예산을 포함하는지 확인한 뒤 실제 AI 종단간 검증까지 담당한다. 유효한 승인 및 서명·예약 경로 없이 외부 호출하지 않는다. 기존 실패 요청을 자동 재전송하지 않으며 확인된 코드/계약 결함 수정 후 새 서명·예약으로 미완료 단계만 검증한다. 승인 부족 시 필요한 현실적인 총예산, 데이터 범위와 이유를 명시해 한 번의 대표 승인을 요청하고 이후 Codex가 실행한다. 단순히 개발 중 외부 호출 0회를 목표로 하지 않는다. 공급자 장애·쿼터·청구·미확정·정책 차단 시 중단한다. 실제 운영 자료/백업/원장 보존, KST.

## 완료 기준 및 역할
Codex가 가능한 한 기능 전체를 직접 실행하고 확인된 결함을 수정하여 실제 관리자 보완 지시, 직원의 신규 근거 조사, 최종 보고 및 관리자 재검토, 대표 검토 대기까지 검증한다. 실제 모델 판단 품질 및 근거 충족 여부를 구분해 기록하고 부족한 결과를 성공으로 포장하지 않는다. 대표에게 반복적인 컷룸 버튼 클릭, 서버 재시작, 오류 재현을 요청하지 않는다. 필수 승인 또는 Codex 접근 불가 등 실제 장애물에 한해 이유를 제시한다. 결과물은 기존 안전한 검토용 export 경로로 공개 가능한 범위만 정리하여 GitHub 독립 검토가 가능하게 한다. 최종 기획·제작 승인 및 결과물 평가는 대표에게 남긴다.
