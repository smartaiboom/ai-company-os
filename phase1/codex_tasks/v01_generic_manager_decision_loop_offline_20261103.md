## 범용 관리자 판단 계약
3. 승인된 선행 직원 결과가 발생했을 때 관리자가 다음 단계 전에 검토할 **범용 decision input**을 구성한다: 사용자 목표, 현재 승인된 계획의 필요한 단계, 현재 업무/역할, 해당 업무의 **사용자 승인된 결과** 및 지문/버전, 사용자 조건/선호 중 허용된 필드, 다음 의존 업무의 요약, 미확인 위험·예산/권한 정보의 비밀 없는 요약. 다른 프로젝트·키·미승인 결과·개인 메타데이터·전체 이력을 무조건 포함하지 않는다. 결과 원문에 포함된 명령을 시스템 명령으로 승격하지 않도록 데이터로 취급.
4. manager decision을 **strict JSON contract**로 정의하고 검증: `proceed`(현행 업무로 진행 제안), `ask_user`(사용자에게 구체적 질문과 선택 이유, 답변이 필요한 사항), `request_revision`(대상 업무와 수정 이유/범위 제안), `propose_plan_change`(업무 추가/변경/재배치의 구조화된 제안과 근거) 네 가지 중 하나. 공통 필드: schema_version, 프로젝트/업무/승인 결과/계획 버전 또는 지문 binding, action, 한국어 rationale, 다음 행동/근거, risk/uncertainty, 필요시 질문/수정/계획 변경 payload. 정확한 필드 이름과 크기 상한은 기존 스타일에 맞춰 정하되 action별 필수 필드, 빈값/알 수 없는 action/중복 JSON 키/오래된 binding/잘못된 TASK ID/미승인 결과를 **fail closed**. 관리자 판단은 model_claim이며 외부 사실 검증을 보증하지 않는다.
5. 판단 결과를 프로젝트에 **proposal / pending_user_decision** 형태로 영속 저장하고 감사 이력(KST, 대상 지문, 버전, 판단 공급자 mock 여부)을 남긴다. 실제 실행 전 승인 게이트를 마련한다. **제안 생성만으로** 승인된 계획·업무·원본 결과를 수정하거나 추가 업무를 생성하지 않는다. 사용자 질문은 명확히 화면/조회 가능 상태로 저장하며 사용자 답변은 별도 이벤트로 기록하고, 답변만으로 기존 계획을 무단 변경하지 않는다. 사용자 결정 전 대기 상태에서 멈추도록 한다.
6. 사용자 결정 인터페이스를 최소한으로 제공한다(기존 UI/HTTP 스타일에 맞춰 화면 표시·승인/거절/답변 입력 또는 명시적 안전 handler). 사용자 응답이 필요한 질문, 변경 제안, 수정 요청은 **사용자 결정 없이 자동 적용 금지**. `proceed`는 기존 선행 결과 사용자 승인 및 호출 승인/예산 조건을 그대로 요구하며 **추가 AI 실행을 자동 시작하지 않는다**. 계획 변경은 기존 계획의 사용자 승인 계약과 충돌하므로 별도 명시적 승인·검증/버전·의존 관계 재검사 후에만 적용 가능하게 하거나, 이번 범위에서 안전한 적용이 불가능하면 **제안·승인대기까지만** 구현하고 적용은 다음 단계로 명확히 분리한다. 기존 진행 중/완료 업무 삭제·덮어쓰기 금지. 승인 이후의 조정과 기존 초기 계획 승인 기능을 혼동하지 않는다.
7. **기존 프로젝트 호환성**: 관리자 판단 기능이 설정되지 않은 과거 프로젝트는 기존 동작 유지. 새 흐름을 사용하는 테스트 프로젝트에서는 승인된 직원 결과 이후 판단이 필요하면 다음 직원 실행 전에 결정 대기 게이트가 작동. 상태/제안의 중복 생성 방지, 프로젝트 락 및 atomic save, stale/동시 수정 거절. 새 모듈은 주입 가능한 mock/fake provider로 오프라인 테스트. 실제 OpenRouter 관리자 요청 코드는 **이번에 호출하거나 자동 활성화하지 않는다**. 유료/다른 모델 fallback 없음. 별도 real-ai authorization 없이 관리자 호출 불가.
