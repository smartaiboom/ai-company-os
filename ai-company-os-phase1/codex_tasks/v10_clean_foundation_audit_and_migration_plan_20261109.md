# AI Company OS v1.0 — 기존 코드 전수 조사 및 깔끔한 새 개발 기반 설계 (1단계: 분석만)

2026-11-09 KST. 사용자 결정: **기존 개발 파일이 수십 개로 복잡하므로 꼭 필요한 기능만 남겨 깔끔하게 시작**. 앞으로 실험과 일회성 진단 결과는 정리하며 개발. **이번 업무는 파일 삭제/이동/대규모 리팩터링이 아닌 인벤토리·의존성 분석·안전한 정리안 보고까지만**. 파일 정리와 새 디렉터리 구축은 보고서를 사용자에게 보여준 뒤 별도 승인.

## 제품 목표
- 최종: AI Company OS = 사용자의 목표를 이해하고, 분야별 전문적 산출물을 만들고, 실제 품질 검토·수정·사용자 평가에서 경험을 축적해 다음 프로젝트 품질을 높이며, 장기적으로 개입을 줄여 자율 운영하는 AI 회사.
- v1.0: 목표 구체화 문답 → 실제 AI 관리자/직원 업무 → 결과물의 실제 품질 확인 및 사용자 피드백 → 경험/선호/수정 이유 저장 → **다음 프로젝트에서 실제 검색·반영**을 확인할 수 있는 최소 종단 간 구조.
- 차별점의 증거: 단일 모델 결과 품질이 아니라, **전문 작업 역량·실제 검토/반복 개선·축적 경험 재사용**이 다음 작업의 결과/개입에 미친 효과 기록.
- 개발 콘텐츠: 향후 'AI Company OS vs ChatGPT' 동일 명령 비교 성장 시리즈. 현재 비교 콘텐츠 제작보다 v1.0 기반 우선. 이중 저장/고정 업무 지시/무조건 AI 회사 우월 주장 금지.
- 기존 최상위 원칙 `AI_COMPANY_OS_CORE_PRINCIPLES.md`와 `AGENTS.md`를 읽고, 그중 최종 자율 운영 원칙과 **이번 새 사용자 단계적 협업·품질 우선 결정**의 차이를 명확히 표시. 이 감사 단계에서 원칙 문서 수정 금지.

## 읽기 전용 조사
1. `git status --short`, branch/HEAD, tracked/untracked, gitignore, 폴더/파일 총수·유형·대략 크기. 운영 중 data·backups·work_history·artifacts·reports와 사용자 비추적 파일 존재 확인; 비밀키/원본 영상·실사용 데이터 출력 금지.
2. 전체 Python 엔트리포인트와 import 의존관계, 외부 provider adapters, 프로젝트 store, 자율 manager/employee, review/revision, local tools, 실제 Gemini35 v1 delivered 및 video v2 profile, tests/fixtures/diagnostics/one-off scripts를 코드 수준에서 식별. 실제 사용하지 않는 것과 단지 테스트/역사 보존용인 것 분리. 실행 여부 추측하지 말 것.
3. 현재 **실제로 작동하고 보호해야 할 최소 핵심**을 기능별로 가리기: AI 관리자·직원 협업, 권한/무료/원장/불확실 요청 보호, KST/storage hash, 프로젝트·사용자 평가·경험 재사용을 위한 기존 데이터 구조, 기존 production_video_v2 도구(실제 영상 품질은 제한적), 인터페이스. 비슷한 Gemini/Groq/OpenRouter 어댑터가 여러 개면 격리 및 원장 계약을 보존하면서 새 v1.0에서는 어떤 provider가 최소 필수인지 구별.
4. 다음 5개 상태로 **파일별 분류표**: A 새 v1.0 재사용 / B 필요한 수정 / C 핵심 자동 회귀 테스트 / D archive(이전 실험·진단·보고서·one-off)/ E 제외 후보(사용 중 아님이 입증된 파일). **D/E도 즉시 삭제하지 않음**. 의존성 및 권한 동의, 이전 코드 역호환 문제가 있으면 위험을 표시. 단순 파일명만 보고 분류하지 말 것.
5. 사용자 입장에서 상위 폴더가 간결해야 함. 새로운 `v1/...` 또는 동등한 명확한 독립 작업 영역이 기존 main·프로젝트 root·module import를 깨지 않는지 비교. 새 폴더·폴더명은 계획서에서만 제안, 아직 만들지 않음. 역사 데이터는 archive 또는 immutable store에 남겨 열람 가능하도록. 실제 기록의 해시/ledger/consent/시작 소진 marker를 만지지 말 것.
6. **향후 개발 정리 정책**: 코어/테스트/진단/자료 구분, 임시 스크립트의 만료/이관 기준, 새 파일 추가 시 기존 코드 재사용 확인, 중복 파일 주기적 감사, 기능 변경 시 오래된 코드를 안전하게 제거하는 절차, 테스트 '핵심 회귀'와 '한 번만 사용한 진단'의 차이. 자동 삭제/무승인 destructive cleanup 금지. Git 추적과 로컬 미추적 파일 차이 명시.
7. 2가지 현실적인 안 비교: ① 기존 Phase1을 선별 정리, ② 같은 repository 안에 새 v1 작업 공간을 만들고 검증된 모듈만 이전. 코드량, 의존성, 이전 위험, 유지보수 관점으로 근거를 제시하고 **한 가지 권장**. 전면 재개발 vs 단순 코드 이동이 아닌, 실제 작동하는 최소 회사의 보존이 목적.

## 절대 금지
기존 코드 파일 삭제/이동/변경, 옛 프로젝트 replay/approve/새 prepare, 실제 AI API 호출, 외부 과금·설치·권한 변경, `git clean/reset --hard` 등. 기록/백업/영상/원장에 대한 쓰기 없음. 조사용 인벤토리/분석과 보고서 작성만 허용. `git status` 출력에서 비밀·미추적 파일 내용 노출 금지. 실제 파일 정리는 후속 사용자 승인과 안전한 백업 후 별도 Codex 작업.
