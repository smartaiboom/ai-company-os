# 다음 작업: mock 품질 검사 HTTP 통합 검증

## 목표
AI Company OS에서 새로 구현한 mock 품질 검사 기능이 실제 HTTP 요청, 화면 HTML, 프로젝트 저장과 함께 올바르게 작동하는지 검증한다. 전체 가상회사 목표와 기존 사용자 승인·최종 확정 동작을 유지하고, **검증 우선**으로 진행한다. 이번에는 자동 수정 루프를 추가하지 않는다.

## 작업 전 필수 확인
- `AGENTS.md`, `codex_tasks/README.md`, `reports/mock_quality_review_implementation_20261102.md`, `reports/autonomous_quality_review_design_20261102.md`와 관련 `app.py`, `quality_review.py`, 테스트를 읽는다.
- 현재 브랜치, origin/main, git status/diff 확인. 기존 추적/미추적 파일·업무 JSON·스냅샷·백업을 모두 보존한다. reset/clean/force push 금지. 시각은 KST.
- 실제 AI API, 외부 제공자, 유료 모델 호출 절대 금지. 테스트 데이터는 TemporaryDirectory로 격리하고 AI 실행 함수를 네트워크 금지 mock으로 대체한다.

## HTTP 검증
1. 실제 loopback HTTP POST /quality/review 요청으로 mock 결과의 필수 제목 통과/누락을 검사하고 응답과 저장된 판정·피드백·KST 시각이 맞는지 확인한다.
2. GET 화면에 공개 검사 기준, 결과 판정, 누락 항목, '형식 검사이며 사실성 검증 아님' 문구가 있는지 확인한다. GET 요청은 JSON 파일 바이트를 변경하지 않아야 한다.
3. 동일 결과 중복 POST에서 감사 기록이나 결과가 불필요하게 늘어나지 않는지 확인한다.
4. 결과 또는 선행 입력을 변경했을 때 이전 판정 stale 표시, 이후 명시적 재검사가 가능한지 확인한다.
5. 실제 AI 엔진 설정/잘못된 대상·규칙·결과 상태에서는 AI 호출 전에 거절하는지, 프로젝트 데이터와 기존 사용자 검토 승인·최종 확정 스냅샷을 보존하는지 확인한다.
6. 동시 평가/승인/실행이 동일 프로젝트에서 409를 반환하는지, 다른 프로젝트 요청은 진행 가능한지 기존 테스트 근거와 필요한 새 HTTP 검증으로 확인한다.
7. 이전 기존 테스트 통과 기록과 이번 직접 실행 결과를 구분한다.

## 브라우저 환경
- Playwright/Chromium이 이미 사용 가능하면 실제 브라우저 클릭·모달·오류 표시도 임시 데이터로 테스트한다.
- 현재 환경에 없다면 기존 무리한 의존성 재설치나 시스템 패키지 변경을 강행하지 말고 HTTP/HTML 테스트로 대체하고 미검증 항목을 보고한다.
- 발견된 운영 오류는 최소 수정과 명시적 회귀 테스트로만 해결한다. 문제가 없으면 운영 코드를 변경하지 않는다.

## 완료 조건과 보고
- 관련 단위/HTTP 테스트 및 안전한 전체 회귀 테스트 실행. 실제 업무 저장 경로를 사용하는 격리되지 않은 smoke 테스트는 실행 금지. git diff --check 확인.
- 반드시 `reports/mock_quality_review_http_validation_20261102.md` 파일을 생성하고 실제 실행 명령·통과/건너뜀 수·보존 증거·변경 내용·미검증 항목·AI 호출 없음 여부를 적고 재독한다. 기존 같은 경로가 있으면 먼저 확인해 보존한다.
- 의도된 테스트/필요 최소 수정/보고서/작업 이력 파일만 선택적으로 스테이징해 origin/main에 안전하게 커밋·푸시한다. 기존 업무 데이터·스냅샷·미추적 파일 포함 금지. 미해결 실패/충돌 시 푸시 중단.
- 원격 보고서 존재와 커밋 SHA 확인. 결과를 대화에만 남기지 않는다.
