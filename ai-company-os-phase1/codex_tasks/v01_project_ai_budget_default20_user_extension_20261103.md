# AI Company OS v0.1 — 프로젝트 기본 AI 호출 예산 20회 + 사용자 승인 추가 예산

## 사용자 확정 정책
“7회는 너무 적다. 한 프로젝트에 20회를 기본으로 하고 필요할 땐 사용자에게 문의하여 횟수를 늘리는 것으로 하자.”
- 프로젝트당 **기본 실제 외부 AI 호출 예산 20회**. 새 프로젝트는 기본 20회. 기존 실제 영상 프로젝트 `cb44b605b498`도 사용자 결정에 따라 7→20으로 안전하게 상향하되 **기존 2회 사용 기록 그대로**(변경 후 2/20, 잔여 18). 이 상향은 **예산만** 변경하며 AI 실제 실행/전송/재개/모델 호출 허가가 아니다.
- 예산 소진 또는 예측 부족 시 **AI 관리자가 근거와 요청 추가 횟수를 사용자에게 제안**, 사용자 승인 전 한도 변경 금지. 승인 시 사용자가 확인한 **추가 횟수만** 증가(예: 20→30), 거절 시 변경 없음. 관리자는 임의 상향/우회/예산 리셋 금지. 예산 증가를 요청하는 판단도 **실제 AI 호출을 필수로 하지 않도록** 잔여 예산 0에서도 작동하는 deterministic 안전 중단·질문 경로가 있어야 함. 실제 AI 관리자 추론이 가능할 때만 사용자 별도 승인된 실제 호출을 사용할 수 있음. 오프라인 기능을 실제 AI 자율 판단이라고 보고하지 않는다.
- 프로젝트당 한도와 **시작·재개 요청당 최대 2회**는 별개다. 기존 2회 제한·명시적 외부 전송 동의·호출별 승인·OpenRouter `openrouter/free` 고정·HTTPS·무재시도·예약 선기록·미확정 예약 보존을 유지한다. 예산 20회로 변경해도 자동으로 20회 연속 호출하지 않는다.
- 이번 Codex 작업 **실제 외부 AI API 호출 0회**, TASK-002 실행 금지, 다른 실제 프로젝트/원장/미확정 예약/기존 백업/미추적 파일 보존. KST 일관 적용. `codex_tasks/README_KOREAN_LANGUAGE_RULE.md` 준수, 결과 보고서 한국어.

## 먼저 기존 구조 확인
1. `git pull --ff-only`. `ai_safety.py`의 `MAX_CALLS=7`, `MAX_CALLS_PER_REQUEST=2`, `check_project_permission`, `request_json`의 `MAX_CALLS * MAX_INPUT_BYTES` 누적 상한과 호출 예약 저장, `app.py`의 실제 프로젝트 생성/실행/동의/저장·락·history, `manager_decision.py`의 permission_summary와 사용자 질문·승인 흐름, 기존 tests/최근 보고서를 관련 범위에서 점검한다. hardcoded 7이나 2/7 UI/테스트/문구를 찾아 필요한 것만 갱신. 단순히 상수 하나만 바꾸고 끝내지 말 것.
2. 기존 실제 영상 프로젝트의 Git 제외 JSON `data/video-real-plan-20261103/projects/cb44b605b498.json`과 다른 프로젝트·백업 경로, SHA, 현재 예산/승인/미확정 상태를 **변경 전** 확인한다. 상태가 보고서와 다르면 중단하고 보고. 프로젝트 c85d9853906a의 미확정 예약은 절대 해소/소비/삭제하지 않는다.

## 구현 요구
3. `DEFAULT_PROJECT_CALL_BUDGET=20` 같은 명확한 기본값과 프로젝트별 영속 `limit`을 구분. 과거 limit 필드가 없는 프로젝트의 기본값 해석과 신규 생성 초기화가 일치하도록 하고, 이전에 명시 저장된 작은 한도(7 등)는 자동으로 20으로 해석해 보안 게이트를 우회하지 않도록 한다. **이번 사용자 요청으로 명시된 영상 프로젝트 cb44b605b498만** 기존 7→20 변경. 다른 기존 프로젝트의 명시 limit는 그대로 보존한다. 입력/출력 누적 크기 제한은 새 예산을 반영하되 안전한 per-call 크기 상한과 전체 총량 상한을 유지한다. 호출 수를 len(attempts) 기준으로 기록(성공/실패/예약 모두 차감), 기존 호출·reservation 불변. 한도 증액으로 미확정 예약의 자동 재전송이 허용되어서는 안 됨.
4. 사용자 추가 예산 요청의 **명시적 상태/데이터 계약**: 프로젝트 ID, 현재 limit/used/reserved, 요청 추가 횟수(양의 정수, 합리적 상한), 필요 사유/예상 사용 계획, 생성 KST, 요청 당시 프로젝트/예산 버전 지문, pending/approved/rejected 상태, 사용자 결정 감사 이력. 가능하면 기존 manager_decision 사용자 질문·승인 구조를 재사용하되 기존 네 action과 충돌하면 별도 좁은 예산 제안 계약을 둔다. 한도 부족 시 사용자가 확인 가능한 요청이 생성/표시되어야 하며, 단순 오류 메시지만 남기지 않는다. 호출 예산 0에서 요청 생성은 외부 API 없이 가능해야 한다.
5. **사용자 승인 처리**: 사용자 의사가 명시된 경우에만 승인/거절, 승인 시 제안에 기재된 추가 횟수만 atomic 증액, 승인 시각 KST/결정 근거 저장, 변경 전후 예산 기록. 중복 승인·stale 제안·다른 프로젝트/권한·동시 요청·동시 승인·과도한 추가 요청 거절. 임의 JSON 변경이나 승인되지 않은 manager_claim만으로 증액 불가. 현재 프로젝트의 소유자 확인/기존 사용자 결정 경계를 존중. 승인/거절/조회 가능한 최소 인터페이스(기존 앱 UI 또는 명시적 안전 handler)를 구현하고 사용 방법을 보고. **제안 생성 자체는 사용자 승인 아님**. 인증되지 않은 공개 HTTP에서 임의 승인 가능하도록 열지 말 것; 기존 권한 구조가 충분하지 않으면 안전한 로컬 도구 방식으로 제한하고 미구현 부분 보고.
6. **AI 관리자 연결**: 현재 `manager_decision.py`는 모의 관리자만 있고 실제 판단 미연결임을 인정. 예산 부족/예측 부족을 확인할 수 있는 비밀 없는 예산 요약과 추가 요청 제안 경로를 범용 업무 흐름에 연결하되, 자동 증액·자동 재호출·자동 실제 모델 판단 금지. 관리자가 필요량을 산정하는 로직을 고정 숫자로 단정하지 말고 사용 이유/필요 작업과 예상 호출 수를 구조화하도록 설계. 오프라인에서 deterministic 예산 소진 감지 및 사용자 요청 생성은 가능하나 이를 ‘AI가 스스로 추론’이라고 주장하지 말 것.
7. 프로젝트 승인/데이터 전송 범위, 모델 무료 제한, 실제 요청마다 필요한 승인 등 기존 보안 계약 유지. 프로젝트 기본 예산 증가는 제공자 OpenRouter의 무료 호출 할당량 보장이나 무료 비용 보장이 아님을 UI/보고서에 명시. 오류/타임아웃/예약은 호출 횟수 소모, 재시도 없음.

## 완료 기준
프로젝트 기본 호출 한도 20회가 새 프로젝트에 적용되고, 사용자 승인한 실제 영상 프로젝트가 2/20으로 안전하게 상향되며, 필요시 추가 횟수를 사용자에게 요청해 **사용자가 명시적으로 승인한 경우에만** 프로젝트 예산을 늘리는 흐름이 오프라인 검증됨. 실제 AI 호출/대본 작성은 수행하지 않음.
