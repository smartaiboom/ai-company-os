# AI Company OS v0.1 — 범용 AI 관리자 응답 계약 개선 (오프라인 전용)

## 목표
실제 OpenRouter 관리자 판단 2회가 각각 유효 제안 저장에 실패했다. 2차 응답은 provider JSON 파싱까지 성공했지만 `decision_contract/strict_contract`에서 거절됐다. 원문은 보존되지 않았으므로 어떤 필드가 잘못됐는지 단정하지 않는다. 현재 `manager_decision.py`의 `RealManagerDecisionProvider`는 모델에게 project_id, result_hash, approval_hash, plan_hash, input_hash 등 **프로그램 소유 binding 전체를 그대로 복사**하게 하고, 여러 필수 설명 필드와 엄격한 action별 payload를 요구한다. 모델의 **실제 판단**과 프로그램이 관리할 **신원·승인·지문**을 분리해, 범용 AI 관리자의 자율 판단을 보존하면서 불필요한 형식 실패를 줄이는 **최소 수정**을 수행한다. 이번 작업에서 실제 AI API 호출 **0회**, TASK-002 실행 **0회**. 오프라인 검증 후 바로 실사용 판단 단계로 돌아가기 위한 작업이며, UI/전체 설계/다른 기능으로 확장하지 않는다.

기존 규칙: `codex_tasks/README_KOREAN_LANGUAGE_RULE.md` 준수, 지시·보고서 한국어, 모든 시간 KST(+09:00), 데이터·백업·미추적 파일 보존, 백업 하루 최대 1개, reset/clean/force push 금지. `git pull --ff-only` 후 실제 소스/테스트와 `reports/v01_real_manager_second_authorized_call_20261103.md`, `reports/v01_manager_decision_offline_diagnostics_saveflow_20261103.md`를 먼저 확인한다.

## 설계 원칙
1. **모델은 자율적으로 행동을 선택**: proceed / ask_user / request_revision / propose_plan_change 중 하나와 한국어 판단 근거, 사용자 질문 또는 다음 업무 지침/변경안을 생성. 콘텐츠의 개수, 특정 action, 영상 전용 규칙을 코드로 강제하지 않는다. 모델은 사용자 승인, 직원 실행, 계획 수정 권한이 없다.
2. **프로그램은 식별·보안 필드 소유**: 모델에게 전체 `binding`의 복사/생성을 요구하지 말 것. 프로젝트/업무/승인 결과/계획/input 지문은 `decision_input`에서 프로그램이 계산하고, 제공자 응답 검증 후에만 프로그램이 **검증된 모델 판단에 binding을 붙여** 기존 `parse_and_validate`/저장·조회/사용자 결정 경로와 호환한다. 모델이 보내는 임의 project_id/binding/approval 표시는 신뢰하거나 채택하지 않으며, 모델이 타 프로젝트·타 TASK를 지정해도 허용하지 않는다. **중요**: binding을 모델 대신 채운다는 이유로 검증되지 않은 action·payload·근거를 승인해서는 안 된다.
3. **단순하지만 엄격한 모델 출력 계약**: 기존 strict 저장 계약은 유지하되, 모델에 요구하는 외부 JSON은 가급적 `action`, `rationale`, `evidence`, `next_step`, `uncertainty`, `payload`의 의미 있는 필드로 단순화. 프로그램 소유 `schema_version`, `binding`, `source=model_claim`은 검증 뒤 조립한다. 모델이 과거 형식의 `binding`/metadata를 출력했을 때 무조건 무시해 통과시키는 우회 금지: 명시적으로 거절하거나 모델이 보내지 말라고 지시하고 일관된 정책 테스트. 허용 키와 값은 문서화하고 중복 키/알 수 없는 action/과도한 크기/타 TASK/형식 오류는 거절. 모델 응답을 '수정'해 의미를 바꾸지 않는다. 출력 형식 예시를 간결하게 제공하되 행동 하나를 강제하는 예시 편향은 피한다.
4. **의미적 안전성 유지**: 한국어 근거/불확실성, 선행 결과의 미검증 주장 분리, 직접 후속 TASK ID 및 승인된 기존 ID만 허용, 추가 계획 변경안은 사용자 승인 대기만, 직원/사용자 텍스트를 system 명령으로 승격 금지. `ask_user` 질문, `request_revision` 대상, `propose_plan_change` 대상도 명확히 검증. 너무 긴 텍스트/허용하지 않은 필드/숫자·빈 문자열/중복 키/JSON 외부 텍스트 거절. 이미 승인된 TASK-001 결과를 덮어쓰지 않음.
5. **기존 모의 계약/저장 형식 호환**: 기존 `MockDecisionProvider`, `parse_and_validate`, `manager_decision_view`, `respond_manager_decision`, `require_proceed`, 기존 승인된 계획·업무 데이터의 schema를 깨지 않도록 새 모델 응답 경계만 최소 수정. 현재 1차·2차 실제 호출 함수의 사전 승인·예산/예약·guard·중복 방지·저장/지문/사용자 승인 대기는 유지. 새로운 호출 권한을 자동 부여하지 않음.
6. **진단**: 모델 응답 형식이 거절되면 기존 `DecisionDiagnosticError` stage/code를 유지하되 비밀 없는 제한된 세부 코드(예: missing_field, invalid_action, invalid_payload, invalid_target, invalid_text, unexpected_field)로 분류할 수 있으면 최소한으로 추가. 모델 응답 전문·API 키·개인 데이터·프롬프트를 일반 로그/Git에 남기지 않는다. 지난 2회 실패의 원인은 알 수 없다고 유지.
7. **테스트 우선, 외부 호출 금지**: 임시 프로젝트+fake transport로 4 action 각각 **모델 소유 최소 JSON → 프로그램 binding/metadata 조립 → 기존 strict 저장 계약 통과 → 원장 completed → `pending_user_decision` 영속 저장/새 프로세스 조회**, 승인 전 TASK-002 차단, 2차 승인 및 guard/예산 회귀. 잘못된 action/payload/TASK ID/한국어/누락·초과 필드/중복 키/크기/JSON/finish_reason/동시 변경은 제안 0·추가 전송 0·안전 중단을 검증. 기존 테스트가 과거 full-binding 모델 응답을 fake로 쓰는 경우, **실제 provider 테스트만 새 출력 형식으로 업데이트**하고 기존 모의 입력 및 내부 저장 계약 테스트는 유지. 실제 API 키/프로젝트 JSON은 테스트에 사용하지 말 것.
8. **보존/예산**: 실사용 프로젝트 `cb44b605b498`는 현재 **4/20, completed 4, failed 0, reserved 0, 잔여 16, 실제 관리자 제안 0, TASK-001 사용자 승인·결과 SHA256 `95e366272746a507f26f3776db5e6e5211126ae0f1f7d2b7712a718e5cff6802`, TASK-002~004 대기**. 기존 두 실제 manager attempt/authorization/additional_authorizations/guard/중단 이력은 불변. 재고 프로젝트 `c85d9853906a`의 미확정 예약 및 모든 data/backups/미추적 파일 불변. 사전/사후 목록·SHA 확인. **절대 실사용 실제 호출 재실행/guard 초기화/사용량 수정 금지**.
9. 보고서 `reports/v01_manager_model_output_contract_offline_20261103.md` 작성: 변경 파일, 모델 출력 계약과 프로그램 소유 필드 구분, 기존 저장 호환, 4 action 오프라인 통합 검증, 집중 테스트 수/결과, 실제 AI 호출 0, 예산 4/20 불변, 기존 업무·다른 프로젝트·백업 보존, 한계 및 **다음 실제 관리자 호출에 새 사용자 승인 필요** 명시. `git diff --check`, 집중 테스트, 필요한 코드·테스트·보고서만 선택적 commit/push, 원격 main 일치 확인.

## 완료 기준
실제 네트워크 없이 **모델이 생성할 최소 판단 JSON**이 네 행동 모두에서 기존 실사용 provider/handler를 통과해 사용자 결정 대기 상태로 안전하게 저장되는지 입증. 실제 관리자 판단이 성공했다고 주장하지 않는다. 전체 회사 구조나 영상별 규칙을 추가하지 않고, 다음 단계는 새 사용자 승인 하에 실제 관리자 판단 검증으로 복귀한다.
