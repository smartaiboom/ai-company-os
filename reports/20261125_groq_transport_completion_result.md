# Groq 표준 클라이언트 검토와 권한 차단

2026-11-25 KST · 최신 GitHub main `1dcd803`에서 시작했다.

## 관측과 로컬 검증

대표는 일반 WSL에서 최소 curl 요청이 HTTP 200, 같은 모델과 최소 메시지의 Python urllib 요청이 HTTP 403이었다고 보고했다. 두 결과는 대표 관찰이며 응답·경유 경로·청구를 독립 검증하지 않았다. Codex는 이전에 16:24:42 협업 요청과 16:41:39 최소 urllib 요청에서 각각 403을 원장에 기록했다. 최소 요청의 `cf-ray` 헤더 존재는 응답 생성 계층을 확정하지 않는다. HTTP 클라이언트, TLS/HTTP 협상, 경유 경로 중 어느 차이가 영향을 주었는지는 미확인이다. [이전 실제 비교](20261125_groq_live_comparison_result.md)

공식 Groq Python SDK는 HTTPX를 사용하며 기본 재시도 설정을 끌 수 있다. 저장소 가상환경에는 SDK·HTTPX·Requests가 없었고, 같은 WSL의 기본 Python에는 Requests 2.32.5가 있었다. 설치나 의존성 파일 추가 없이 이 설치본으로 임시 후보를 검토했다. dotenv 키가 이전 서명의 키 결합과 일치하는지 로컬에서 확인했으며 키 값과 인증 헤더는 출력하지 않았다. [Groq Python SDK](https://github.com/groq/groq-python) · [HTTPX 클라이언트 설정](https://www.python-httpx.org/api/#client)

응답을 모의한 로컬 테스트로 고정 HTTPS POST 목적지 외 차단, TLS 검증 활성화 파라미터, 환경 프록시 미사용, 타임아웃 전달, 307 후속 요청 차단, 재시도 0, 제한된 본문 읽기, 403 코드 추출을 확인했다. 로컬 테스트는 실제 TLS 핸드셰이크나 Groq 권한을 확인하지 않는다. 임시 진단은 기존 서명·선예약·원장 경로를 사용하도록 준비했다.

## 실행 제한과 재개 조건

**자동 권한 심사가 Requests 최소 진단 외부 실행을 거절했다.** 심사 사유는 기존 HTTP 403 이후 클라이언트 결함과 정상 허용 경로가 입증되지 않은 상태에서 다른 클라이언트로 동일 최소 메시지를 전송하면 순차 재시도가 될 수 있다는 것이다. 프로세스가 시작되지 않아 이번 실제 API 요청·새 서명·예약은 모두 0건이다. 기존 원장과 전송 코드를 보존했으며 보고서만 반영했다.

실제 관리자·직원 업무, 수정 의견 반영 및 영상 인계는 미실행이다. Groq 잔량과 청구는 미확인이다. 지원 문의에 필요한 자료는 이전 두 요청의 KST 시각, 고정 모델과 API 경로, HTTP 상태, 최소 요청의 옵션과 헤더 존재 여부다. 문의는 발송하지 않았다. 공급자나 네트워크 관리자가 거절 근거 또는 정상 허용 경로를 확인해야 신규 진단의 실행 승인 심사를 다시 진행할 수 있다. 이후 새 서명·예약으로만 신규 협업을 시작한다.
