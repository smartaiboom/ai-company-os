## 범용 검토 경로의 최소 설계
1. 기존 승인 후속 판단 입력과 별도로 **명시적 review 목적의 읽기 전용 context**를 만든다. TASK-002 같은 `status=완료`, 결과 문자열 존재, `review_status=pending`, 승인된 계획/업무 정의와 일치, 승인된 선행 결과가 있는 대상만 허용. 이미 승인된 TASK-001의 기존 경로는 그대로. 검토 입력에는 `purpose=employee_result_review`처럼 명시적인 구분, 대상 result revision/hash, **pending 검토 상태/지문**, 승인된 계획 hash, 프로젝트 목표·관련 선행 승인 결과 및 사용자가 승인한 관리자 지침, 다음 의존 업무 정의, 사용자 선호와 안전 예산 요약만 포함. 원문 길이/개인정보·비밀/허용 크기 제한과 자료·지시 격리 준수. 기존 context/저장 계약과의 충돌·다른 프로젝트 접근 차단.
2. 관리자 모델은 **검토 판단**을 자율 생성. 기존 `RealManagerDecisionProvider`의 6개 모델 필드와 프로그램 소유 binding/metadata, `parse_and_validate`, 4가지 행동 의미 검증·중복 키/타깃/한국어/크기 검증을 최대한 재사용. 단, `proceed`를 검토 단계에서 곧바로 후속 직원 실행 허가로 해석하거나 `request_revision`을 자동 실행하지 말 것. 미승인 결과를 대상으로 한 검토 제안은 사용자 결정 대기로 저장되며, **검토 대상이 아직 pending인 동안에는 TASK-003으로 넘어갈 수 없다**. `request_revision`의 payload는 정확한 TASK-002 대상만 가리키도록 검증. `ask_user`는 실제 질문으로 저장하되 자동 답변 금지. `propose_plan_change`는 제안만 저장. 관리자 검토 결과가 긍정적이더라도 사용자 결과 승인은 별도 절차.
3. **사용자 검토 대기 상태의 관리자 제안과 승인된 후속 실행 허가를 구별**하는 목적·지문·저장 계약을 명확히 한다. 기존 `require_proceed`는 승인된 TASK-001→TASK-002의 기존 제안만 계속 인정하고 새 pending-review 제안으로 우회되지 않도록 한다. 중복·stale·경합·결과 변경·검토 상태 변경 시 검토 제안 거절. 이전 proposal과 새 review proposal을 혼동하거나 덮어쓰지 않는다. 새 검토 제안에 대해 사용자가 `approve`해도 직원 결과가 자동 승인되거나 수정되지 않아야 한다. 기존 사용자 승인·검토 상태 변경 API가 있으면 이를 그대로 사용하되 이번에는 **실사용 대상에 적용하지 않는다**.
4. 실제 외부 관리자 검토 호출을 위한 **별도 명시 승인·원장 1회 예약·고유 O_EXCL guard·중복 방지**를 후속 단계에서 안전하게 연결할 수 있도록 오프라인 인터페이스와 테스트만 준비. **이번 지시서에서는 실제 키를 사용하거나 네트워크를 호출하는 runner 실행 금지**. 기존 관리자 1~3차 승인 ID나 직원 TASK-002 승인을 재사용해서 호출 가능하게 만들지 않는다. 6/20 원장을 변경하지 않는다. 이미 제공된 동의 범위를 확대하지 말 것.
5. 기존 안전성 경계를 유지하면서 **최소 코드 수정**. 일반적인 직원 결과 검토에 쓸 수 있는 구조로 만들고 동영상 전용 조건/고정 문구/수정 프롬프트로 결과를 몰아가지 말 것. 필요한 경우 pending 결과의 승인 이전 검토와 approved 결과의 후속 판단을 별개 명시 함수/입력 모드로 분리하되 저장/검증 로직은 공유한다. 기존 1~3차 관리자·직원 단일 호출 도구의 재사용 방지 및 승인된 결과 판단 회귀를 유지.
