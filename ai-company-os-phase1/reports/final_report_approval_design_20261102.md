# 최종 산출물 승인·확정 절차 분석 및 최소 설계

작성: 2026-11-02 KST (조사 시작 11:50)
기준 커밋: `e7317c40064db43d014c620e36f99c7128bf4b77` (main/origin/main 일치)
성격: 분석·설계만 수행. 아래 함수·필드·절차 중 '제안'은 아직 구현되지 않았다.

## 1. 현재 동작의 근거

| 근거 | 현재 동작과 영향 |
| --- | --- |
| `app.py:_task_has_dependents` | 배열 뒤쪽 업무의 해석된 input_task_ids에 현재 ID가 있는지 판단한다. '최종 보고'라는 이름이나 관리자 역할로 최종 업무를 선정하지 않는다. 연결 오류는 이 함수에서는 건너뛰고 실제 실행 시 검사한다. |
| `task_review_status` | 후속 연결이 있는 완료 결과의 구형/검토 불필요 상태를 pending으로 해석한다. 후속 연결이 없는 구형 결과는 기본 not_required다. 단, 기존에 명시된 pending/approved 등 유효한 상태는 유지될 수 있다. |
| `_reset_review_approval`, `execute_project_task` | 새 실행 성공 및 결과 변경 시 후속 연결 유무에 따라 pending/not_required로 초기화한다. 따라서 마지막 업무뿐 아니라 중간의 독립된 말단 업무도 검토 불필요일 수 있다. |
| `task_review_controls` | 후속 연결이 없으면 바로 빈 문자열을 반환하므로 최종 결과의 승인·수정 요청 폼이 없다. |
| `Handler._handle_post`의 `/task/review` | 후속 연결이 없으면 검토 요청을 거절한다. 상태만 pending으로 바꿔도 최종 결과 승인 기능은 생기지 않는다. |
| `task_has_successful_result` | 해당 업무의 최신 관련 이력(task_execution_succeeded/failed/task_result_saved)을 역순으로 찾아 최신 저장 결과가 실행 성공에 대응하는지 판단한다. 결과 본문 해시·고유 실행 버전 검사는 아니다. 수동 저장은 성공 이력을 무효화한다. |
| `_validate_task_predecessors` | 명시적/구형 연결 해석, 선행 완료·재검토 해제·비어 있지 않은 결과·검토 승인을 요구한다. 실행은 추가로 모든 앞선 업무의 완료를 요구한다. |
| `run_mock_workflow` | 새 결과가 pending이면 정지한다. 현재 마지막 결과는 보통 not_required이므로 별도 최종 승인 정지가 없다. mock 전용·최대 5개·프로젝트 잠금은 이미 있다. |
| `mark_downstream_for_review`, `/task/update` | 선행 결과/상태 변경은 뒤쪽 진행 중·완료 결과를 보존하며 재검토 대상으로 표시한다. 의존성 그래프만이 아니라 배열의 뒤쪽 전체를 보수적으로 처리한다. |
| `Handler.project_report` | 저장된 업무를 HTML로 집계한다. 완료율과 미완료 목록은 완료/재검토를 기준으로 하고 검토 승인을 별도 완료 조건으로 보지 않는다. 보고서는 언제든 열 수 있으며 확정 스냅샷이 아니다. |
| `save_project`, `project_mutation_lock` | JSON을 .json.tmp 작성 후 replace한다. 앱 POST의 프로젝트 잠금은 단일 프로세스에서 판정부터 저장까지 보호하지만 JSON과 별도 산출물 파일을 하나의 트랜잭션으로 저장하지는 않는다. |

최종 보고 역할의 task.result가 JSON에 있는 것, `/report/{id}` HTML을 볼 수 있는 것, 사용자가 최종 산출물을 확정한 것은 서로 다른 사실이다. 프로젝트 상태 completed도 현재 사용자가 선택할 수 있으므로 확정의 증거로 사용하면 안 된다.

## 2. 대안과 선택

| 대안 | 장점 | 문제 |
| --- | --- | --- |
| 모든 말단 업무를 최종 승인 대상으로 삼음 | 여러 산출물 처리 가능 | 범위가 넓고 어느 결과를 대표 보고서로 확정할지 추가 선택 정책 필요 |
| 업무명 '최종 보고'로 찾음 | 간단함 | 실제 계획은 이름·역할·업무 수가 가변이며 이름 변경·중복에 취약 |
| 별도 최종 검토 업무를 자동 삽입 | 기존 후속 게이트 활용 | 계획·ID·연결을 바꾸고 중복 검토 업무나 순환 오해를 만들 수 있음 |
| **현재 순서형 계획의 마지막 업무를 최종 대상으로 지정하고 기존 검토 경로 재사용** | 최소 변경, 기존 직렬 흐름과 일치 | 다중 최종 산출물·순서 변경은 후속 설계 필요 |

마지막 대안을 선택한다. 첫 버전의 최종 대상은 tasks 배열의 마지막 업무 하나이며, 빈 배열이면 대상 없음이다. ID는 비어 있지 않고 프로젝트 내 유일해야 한다. '최종'이라는 이름을 요구하지 않는다. 배열 끝이 실제 목표 전체를 대표한다는 의미적 보장은 없으므로 화면에 최종 대상 업무 ID·이름을 명시한다. 임의 말단 업무 전체의 승인을 새로 강제하지 않는다.

## 3. 상태와 화면 판정 (제안)

기존 task.status, review_required, review_status를 유지하고, 프로젝트 수준의 final_report 참조를 선택적으로 추가한다. 하나의 상태 필드에 실행 완료·승인·파일 보관을 섞지 않는다.

| 화면 상태 | 정확한 조건 |
| --- | --- |
| 최종 결과 미생성 | 대상 없음 또는 결과가 없거나 실행 미완료 |
| 재실행 필요 | 실패/재검토 표시, 최신 성공 이력 없음, 선행 조건 불충족. 기존 결과는 표시하되 확정 불가 |
| 최종 검토 승인 대기 | 최종 업무 완료, 비어 있지 않은 결과, 최신 성공 이력, 모든 앞선 업무 완료·재검토 해제, 필수 선행 결과 승인 조건 충족, 현재 최종 승인은 없음 |
| 최종 수정 요청됨 | 검토 상태 changes_requested. 승인 버튼은 차단하고 의견과 개별 재실행 안내 표시 |
| 보관 확인 필요·확정되지 않음 | 검토 승인 정보만 있거나 참조 스냅샷 누락·파싱 실패·내용 불일치. 검토 승인과 확정을 동일시하지 않음 |
| **최종 보고서 확정** | 위 실행·입력 조건 유지 + 대상 review_status=approved + 현재 final_report 참조와 보관 JSON이 존재·유효 + 현재 근거 지문과 스냅샷의 지문 일치 |
| 최종 확정 무효·재검토 필요 | 과거 확정은 있지만 대상·내용·근거·유효 상태가 변경됨. 과거 스냅샷은 유지 |

진행률에는 '업무 실행 완료율'이라고 명시하고, 별도로 '최종 확정 여부'와 선행 승인 대기 개수를 표시한다. 실행 100%라도 미승인이면 '최종 검토 승인 대기'다. `/report/{id}`의 미확정 화면 제목은 '작업 결과 현황 · 미확정', 유효 확정 시에는 '최종 보고서 · 확정 vN'으로 표시한다. 보고서 GET은 파일 생성·상태 갱신을 하지 않는다.

## 4. 한 개의 작은 후속 구현 작업

**후속 작업명: 마지막 업무의 사용자 최종 승인과 JSON 스냅샷 보관.** 새로운 AI 실행이나 별도 최종 업무를 만들지 않고 기존 `/task/review`의 최종 승인 동작을 확장한다. Markdown 내보내기·다중 산출물·독립 검토 프로세스는 제외한다.

예상 파일/함수 변경:

- `app.py`: `final_task_index(project)`와 `task_needs_approval(project, index)`를 추가한다. 승인 필요 조건은 기존 후속 연결 있음 OR 마지막 업무다. `_task_has_dependents` 자체의 의미는 바꾸지 않는다.
- `task_review_controls`, `/task/review`, `execute_project_task`, `_reset_review_approval`, `mark_downstream_for_review`, `/task/update`: 승인 필요 판정을 공통화하고 마지막 업무도 pending/수정 요청/재실행/재승인 흐름에 포함한다. 구형 마지막 결과 not_required는 읽을 때 pending으로 해석한다. 기존 approved만 믿어 확정으로 승격하지 않는다.
- `/task/review`: 현재 성공 이력·비공백 결과·재검토 해제 및 기존 선행 검증을 재사용한다. 최종 승인에는 모든 앞선 업무의 완료/비공백 결과/재검토 해제도 검사한다. 연결된 필수 업무는 기존대로 승인되어야 한다. 최종 변경 요청은 비공백 의견 필수, 결과 보존, 재실행 전 즉시 승인 금지다.
- `run_mock_workflow`: 최종 결과도 pending이 되면 즉시 정지하고 '최종 검토 승인이 필요합니다'를 기록한다. 최종 수정 요청은 개별 수정·재실행을 안내하고 자동 수정 루프를 만들지 않는다.
- 보관 로직은 `app.py` 안의 작은 순수 지문 계산/스냅샷 저장/유효성 검사 함수로 시작한다. 최종 승인 요청도 기존 프로젝트 잠금을 끝까지 유지한다. 예상 helper: `final_report_fingerprint`, `archive_final_report`, `final_report_state`, `invalidate_final_report`.
- `Handler.project_detail`, `project_report`: 위 상태표와 대상 업무, 승인/수정 폼, 버전·확정 일시·미확정 이유를 표시한다. 사용자 선택 project.status와 구분한다.
- `tests/test_final_report_approval.py` 신규 및 기존 UI·최종 E2E·mock 조정 테스트의 기대 결과를 수정한다. 예상 문서: 해당 구현 보고서, 작업 이력, 필요시 README의 확정/보관 설명. `execution_engine.py`, 무료 모델 검사, 외부 의존성은 변경 대상이 아니다.

기존 프로젝트를 열었다는 이유로 파일을 고치지 않는다. 누락 필드는 미확정으로 해석한다. 성공 이력 없는 구형/수동 결과는 보존하고 재실행 후 검토하도록 한다. 프로젝트 상태를 completed로 바꿔도 승인 게이트를 통과하지 못한다.

## 5. 추적 가능한 보관 형식과 실패 처리

최소 산출물은 `data/artifacts/{project_id}/final_reports/v000001.json` 같은 불변 JSON 하나다. 별도 Markdown은 다음 단계에서 JSON으로부터 생성한다. 스냅샷에 승인된 결과 본문과 당시 목표·계획·업무 결과/참조를 자체 포함하여 운영 JSON이 나중에 바뀌어도 내용을 확인할 수 있게 한다. 키·토큰·환경 변수·인증 헤더는 담지 않는다.

제안 필드:

| 위치 | 필수 내용 |
| --- | --- |
| 프로젝트 final_report | format_version, version, snapshot_relative_path, fingerprint, final_task_id, confirmed_at(KST), confirmed_by='사용자', status(confirmed/invalidated), invalidated_at/reason(해당 시) |
| 스냅샷 | format_version=1, project_id, version, confirmed_at(+09:00 ISO), approved_by, review_status=approved, final_task_id, 최종 결과 본문, 프로젝트/관리자 목표·계획, 업무별 ID·순서·결과·상태·승인 상태·성공 근거, 입력 연결 참조·결과 해시, fingerprint |

지문은 정렬 키·고정 인코딩의 표준화 JSON에 SHA-256을 적용한다. 범위는 목표/관리자 목표, 실행 관련 계획 단계, 업무 순서·ID·name/role/inputs/input_task_ids/output/risk/result, 업무 실행·재검토·승인 상태 및 업무별 최신 성공/수동 저장/실패 근거다. 현재 상태와 비교할 때 목표 변경도 감지한다. 전역 updated_at, 일반 history 추가, 프로젝트 표시용 상태 변경, workflow 중단 기록 등 내용과 무관한 값은 제외한다. 최종 업무의 승인 필드만 승인 직후 형태로 정규화하여 승인 기록 추가 자체가 바로 지문을 바꾸지 않도록 한다. 입력 ID 누락·중복·미래/순환 참조 등은 확정 전에 거절한다. 해시는 사실성 증명이 아니라 동일 내용 판정이다.

저장 순서: 프로젝트 잠금 → 최신 데이터 재조회·검증 → 최종 승인 적용 후보 객체와 지문 구성 → 새 버전 스냅샷 저장 → 프로젝트의 최종 승인/참조·이력 저장 → 성공 응답. 버전은 프로젝트 참조만이 아니라 보관 디렉터리에 이미 존재하는 번호까지 고려해 다음 번호를 택한다. 기존 파일은 절대 덮어쓰지 않고 배타적 생성으로 충돌을 거절한다. JSON 전체 직렬화 후 작성하며 성공적으로 닫히고 다시 읽어 검증된 파일만 참조한다.

파일 두 개를 원자적으로 커밋했다고 주장하지 않는다. 스냅샷 쓰기/재독 실패 시 프로젝트 승인 참조를 저장하지 않고 오류를 반환한다. 스냅샷 저장 뒤 프로젝트 저장이 실패하면 참조되지 않은 파일을 보존하고 미확정으로 남긴다. 재시도는 기존 파일을 덮지 않고 새 번호를 쓴다. 중간 중단으로 부분 작성된 파일도 자동 삭제하지 않고 번호를 점유한 실패 보관물로 취급한다. 화면은 유효한 프로젝트 참조·완전한 스냅샷·일치 지문이 모두 있는 경우만 확정으로 표시한다. 같은 유효 확정에 대한 중복 승인은 추가 버전을 만들지 않고 기존대로 중복 승인 오류를 반환한다.

승인 필드만 있고 유효한 스냅샷 참조가 없는 구형/손상 상태는 중복 승인 성공으로 처리하지 않는다. 사용자가 개별 업무를 재실행해 pending으로 만든 뒤 새 승인 절차를 밟게 한다. 자동 파일 복구는 하지 않는다. 화면 상태가 겹치면 재실행 필요·수정 요청·무효 상태를 확정보다 우선하며, 확정 조건은 모두 충족해야 한다.

경로는 앱이 검증한 project ID와 서버 생성 버전에서만 만들며 사용자가 임의 경로를 보내지 않는다. 원문 보관은 장기 개인정보 보유 위험을 수반하므로 자동 Git 스테이징/외부 업로드를 하지 않는다. 보관물 삭제·정리·복구 정책은 별도 사용자 지시가 있을 때만 도입한다.

## 6. 확정 무효화 기준

이미 확정된 파일은 수정하지 않는다. 현재 프로젝트의 활성 참조만 invalidated로 전환하고 시각·이유를 기록한다. 결과/상태 변경 처리 시 공통 무효화 helper를 호출하고, 조회 시에도 지문·승인 조건 불일치를 계산하여 누락된 무효화 처리가 있어도 확정으로 표시하지 않는다. 조회는 판정만 하고 저장하지 않는다.

- 최종 결과 본문·대상 ID·업무 순서 변경, 최종 상태의 완료 이탈, 재검토 표시, 수동 저장으로 성공 근거 변경: 즉시 무효. 수동 변경 결과는 재실행 전 승인 불가.
- 앞선 업무의 결과 또는 실행/재검토 상태 변경, 승인 철회·수정 요청, 재실행 시작/실패: 최종 확정을 무효화한다. 기존 배열 순서 기반 보수적 후속 재검토 규칙을 유지하고, 직접 연결 여부로 범위를 축소하지 않는다.
- 최종 결과 수정 요청: 승인·활성 확정 무효, 기존 결과와 과거 파일 보존. 의견 전달→개별 재실행→새 pending→재승인 후 새 버전 보관.
- 목표/관리자 목표 또는 실행 관련 계획·입력 연결·담당 역할·산출물 지시 변경: 지문 불일치로 무효. 목표만 바뀐 경우에도 이전 최종 결과를 그대로 재승인하는 우회를 막도록 최종 업무를 재검토 필요로 만들고 재실행을 요구한다. 재계획과 기존 tasks 불일치가 남아 있으면 확정을 거절하고 계획 적용을 별도 확인해야 한다.
- 결과가 같아도 재실행 시작, 실패, 수동 결과 저장 등 검토 근거가 바뀌면 무효다. 새 성공 후 재승인이 필요하다. 단순 표시용 프로젝트 상태·updated_at 변경, unrelated workflow 이력 추가만으로는 무효화하지 않는다.
- 참조 파일 누락/파손·지문 불일치도 미확정으로 판정하고 경고한다. 과거 보관물을 자동 복구하거나 현재 결과로 덮어쓰지 않는다.

## 7. 소켓·실데이터 없는 테스트 제안과 완료 기준

TemporaryDirectory로 PROJECTS_DIR/ARTIFACTS_DIR 모두 교체하고 Handler를 직접 호출한다. 계획/실행 네트워크 함수는 호출 시 실패하는 mock, 실행기는 고정·지연 mock을 쓴다. 아래는 **제안이며 이번에 실행하지 않았다.**

1. 가변 이름·역할·업무 수에서 마지막 ID만 최종 대상으로 선택. 빈 목록/중복 ID/잘못된 연결은 확정 불가. 기존 구형 JSON은 미확정이며 읽기만으로 파일 바이트 불변.
2. 마지막 성공 실행은 완료+pending, 폼 표시, mock 자동 진행이 최종 승인 대기에서 정지. 100% 완료여도 미확정 표시. 성공 이력 없음·실패·빈 결과·재검토·미승인 입력은 승인/파일 생성 전에 거절.
3. 최종 수정 의견 필수. 요청 후 즉시 승인은 거절. 재실행 입력에 의견이 전달되고 실패/빈 응답은 기존 결과·수정 요청 보존. 성공 후 pending, 사용자 승인 시 v1 JSON·프로젝트 참조·KST 이력 일치.
4. 동일 유효 승인 재제출은 버전 증가 없음. 잠금이 걸린 실행/승인 경합은 409, 다른 프로젝트는 진행 가능. 승인 중 엔진 호출 없음.
5. 선행 결과·상태·승인·목표·입력 연결·순서 변경 각각에서 무효화와 과거 파일 바이트 불변. 표시용 상태/workflow 이력만 바꾸면 확정 유지. 재실행·재승인 후 v2가 생기고 v1 보존.
6. 스냅샷 쓰기·재독 실패, 프로젝트 저장 실패, 파일 누락/파손, 버전 충돌을 mock으로 주입. 거짓 확정 없음, 기존 JSON/결과/파일 보존, 재시도는 새 번호 사용. 미참조/부분 파일은 자동 삭제하지 않음.
7. 기존 결과 전달·무료 모델 검사·모의 자동 진행 상한·중복 실행 보호 회귀 통과. 실제 엔진 자동 진행 거절 유지, 키·인증 정보가 보관 파일에 없음.

후속 구현 완료 기준은 위 시나리오의 실제 통과 기록, 화면 상태표와 저장 상태 일치, 두 파일 저장 실패 시 확정 오표시 없음, 과거 버전 보존, 실제 AI 호출 없음이다. 그 전에는 설계가 구현·검증됐다고 보고하지 않는다.

## 8. 이번 조사와 미확인 위험

읽은 근거: AGENTS, codex_tasks/README·task_history·지시서, 현황 분석 보고서, mock 조정 보고서, HTTP/브라우저 보고서, app.py와 승인·UI·E2E·품질·mock 조정 테스트. 기존 코드의 행위와 제안 상태 전이를 대조했다. 실제 업무 JSON·결과·비밀 설정은 읽지 않았다.

실행한 확인: `git status --short`, 브랜치 확인, `git pull --ff-only`, `git diff --stat`, `git diff --cached --stat`, `git rev-parse HEAD origin/main`, `cat`/`sed`/`rg`, KST `date`. 새 보고서 경로가 없음을 확인하고 작성했다. 보고서 재독 및 `git diff --check`로 형식을 확인한다. **이번 테스트 실행 없음**, 실제 AI API 호출 없음, 외부 의존성 설치 없음. 직전 보고서의 77개 중 76개 통과/브라우저 1개 skip은 과거 실행 기록이며 이번 결과가 아니다.

남은 위험: 마지막 배열 항목이 의미상 전체 산출물을 대표하는지는 사용자 확인이 필요하다. 현재 성공 이력은 문자열 기반이므로 강한 실행 버전 추적이 아니다. 제안 스냅샷도 파일시스템 두 파일의 완전한 원자성·전원 장애 내구성·다중 프로세스 동시성까지 제공하지 않는다. mock 품질은 사실성 검증이 아니다. 브라우저 환경 부재도 이전과 같아 실제 화면 조작 검증은 별도다. 이러한 범위는 후속 작업의 완료 보고에 명시해야 한다.

이번 생성 파일은 이 보고서 하나다. 운영 코드·테스트·기존 보고서·업무 데이터·백업·작업 이력은 수정하지 않는다. 이 보고서만 커밋·푸시하고 SHA 및 원격 보고서 존재를 확인한다.
