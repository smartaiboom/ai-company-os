# mock 품질 수정 1회 및 재평가 구현

작성: 2026-11-02 12:51 KST
기준: `5c364b03befa4a98dea0a4293d72788995a1af16` (main/origin/main fast-forward 동기화 후 착수)

## 실제 구현

- `app.py:/quality/revise-once`는 사용자가 명시적으로 요청한 정확한 업무 ID 하나만 처리한다. mock 모드, 현재 결과에 일치하는 성공한 changes_needed 판정, 결과 revision/hash·입력·정책 binding, 완료·성공 이력·선행 승인 조건을 검사한다. pass/inconclusive/stale, 실패/빈 결과, 사용자 수정 요청·의견, 사용자 승인된 업무 또는 프로젝트의 confirmed 참조는 거절한다.
- 수정 후 사용자 승인을 받을 수 있도록 기존 승인 경계가 있는 업무(후속 연결 또는 마지막 업무)만 지원한다. 다른 독립 중간 말단 업무는 승인 절차를 임의 확장하지 않고 거절한다.
- 실행 전에 quality_revision_once 예약을 프로젝트 JSON에 저장한다. operation_id, 원래 review_id/binding, 소비된 attempts=1, phase=reserved, KST 시각·이유를 기록한다. 예약 저장 실패 시 실행기를 부르지 않는다. 기록이 이미 있으면 중복 요청·재시작·품질 재검사 후에도 추가 수정하지 않는다.
- `execute_project_task`는 객체 identity로 구분하는 서버 내부 권한 인자만 이 경로에 허용한다. 예약과 최신 판정을 다시 검증하고 실행기를 `execute_task_mock`에 고정한다. HTTP 폼의 가짜 내부 권한 플래그로는 재실행을 허용하지 않는다. 사용자 review_status를 가짜 changes_requested로 만들지 않는다.
- 기존 선행 결과 검증·담당 역할·성공/실패 검사·후속 재검토·최종 확정 무효화 로직을 재사용한다. 기계 의견은 previous_results의 별도 '자동 품질 검토 수정 의견' 항목으로 같은 task_id에 전달하며 사용자 review_feedback을 덮어쓰지 않는다.
- 수정 실행의 결과는 메모리 후보 객체에서만 만든다. 기존 형식 평가 부분을 `attach_quality_review`로 공유해 후보를 최대 1회 재평가한다. 성공한 후보는 새 revision, pass/changes_needed/inconclusive 판정, stopped 상태와 사용자 승인/확인 필요 이유를 한 번 저장한다. 승인 대상의 review_status는 pending이며 사용자 승인·스냅샷 생성을 자동 수행하지 않는다.
- 실행 실패/빈 결과, 평가 예외·잘못된 판정, 후보 저장 오류에는 예약 직후의 이전 성공 결과/사용자 상태를 기준으로 오류 기록을 저장하고 정지한다. 재평가 오류는 주기 기록에 inconclusive로 표시하고 현재 결과의 기존 품질 판정은 보존한다. 저장 장치가 계속 실패해 오류 기록도 저장되지 않으면 디스크의 reserved 기록으로 추가 실행을 막는다.
- UI에 mock 전용 '수정 1회 및 재검토', 현재 형식 판정, 수정 후 재평가 상태, 마지막 중단 이유, 남은 횟수 및 사용자 승인 별도 안내를 추가했다. reserved는 '처리 중 또는 중단된 예약·자동 재시도 금지'로 표시한다. GET에서 상태를 저장하거나 재개하지 않는다.
- 새 POST는 기존 프로젝트 잠금에 포함한다. 동일 프로젝트의 중복 수정·승인·실행은 409, 다른 프로젝트는 독립 처리한다. 기존 단일 수동 실행과 `/workflow/run`은 별도 명시적 동작으로 유지한다.

## 수정·평가 횟수와 보장 범위

하나의 승인된 명시적 수정 요청은 **수정 실행 최대 1회, 새 결과 평가 최대 1회**다. 자동 연속 반복이나 다른 업무 실행은 없다. 재평가 뒤 여전히 changes_needed라도 재요청은 추가 실행하지 않는다.

이번 최소 구현은 업무별 **보존되는 수정 예약 하나**만 지원한다. 동일 품질 주기뿐 아니라 수동 재실행·새 평가로 review_id가 달라져도 기존 예약을 자동 초기화하지 않는다. 새로운 수정 주기를 여는 조작/횟수 재설정은 구현하지 않았다. 사용자가 별도 확인할 후속 범위다. 임의 파일 삭제로 주기를 초기화하지 않는다.

단일 프로세스의 기존 프로젝트 잠금과 성공적으로 저장된 예약을 전제로 한다. 서버 재시작 후 reserved/error/stopped는 그대로 소비된 시도로 취급하며 자동 재실행하지 않는다. attempts는 예약된 시도 수이며, 실행 전에 중단돼 실제 실행이 없을 수도 있다. 재평가 중 프로세스가 끊기면 저장된 reevaluation_attempts가 실제 도달 횟수를 완전히 복원하지 못할 수 있으나 예약 때문에 새 평가/수정을 재개하지 않는다. 다중 프로세스의 동시 예약, 외부 JSON 편집, 전원 장애 내구성, exactly-once를 보장하지 않는다.

검증한 사례:

- 실행 오류/빈 결과·재평가 예외에서 이전 성공 result/revision/status/사용자 상태·기존 품질 판정 보존.
- 실제/별칭/불명확한 모드, stale/pass/inconclusive, 실패/빈 결과, 사용자 의견·승인 상태 거절 및 요청 전후 파일 바이트 불변.
- 예약 저장 실패의 실행 0회, 후보 저장 실패 후 1회 소비, 오류 기록 저장도 계속 실패한 경우 reserved 유지와 다음 요청 거절.
- 재시작을 모사한 reserved JSON의 추가 실행 거절·GET 파일 바이트 불변. 실행 중 중복·승인 409 및 다른 프로젝트 동시 처리.
- 최종 확정된 결과의 임의 수정 거절과 과거 스냅샷 바이트 보존. 선행 결과 변경으로 이미 무효화된 프로젝트에서의 수정은 후속 재검토·기존 보관 파일 보존을 유지.
- 수동 HTTP 실행 요청에 가짜 내부 권한 문자열을 보내도 완료 결과 재실행 불가.

TemporaryDirectory로 projects와 artifacts 모두 격리했고 네트워크 함수는 호출 금지 mock이다. 개선 결과는 테스트의 명시적인 이전/다음 fixture이며 실제 mock이 의견을 이해해 지능적으로 개선한다고 주장하지 않는다. 신규 테스트는 직접 핸들러와 Event/ThreadPoolExecutor로 실행했다. 전체 회귀의 HTTP는 loopback만 사용했다.

`git diff --check` 통과. 실제 AI API 호출 **없음**, 실제 비밀 키·설정 접근 **없음**, 유료 서비스/외부 의존성 설치 **없음**. 기존 데이터와 스냅샷은 건드리지 않았다. 같은 보고서 경로가 없음을 확인하고 신규 작성 후 재독한다.

## 한계와 다음 단계

- 형식 통과는 제목 존재만 확인하며 실무 품질·사실성·코드 실행을 검증하지 않는다. 자동 품질 판정은 사용자 승인과 최종 확정을 대체하지 않는다.
- 예외/저장 실패 시 후보를 확정하지 않고 원래 결과를 보존하도록 처리하지만, 파일 교체 직후의 전원 장애나 저장 장치가 불확실하게 성공/실패를 보고하는 상황의 완전한 트랜잭션은 보장하지 않는다. 기존 JSON 임시 파일 교체와 예약 기록의 한계를 유지한다.
- 현재 confirmed 참조가 있는 프로젝트, 승인된 대상 업무, 사용자 수정 요청은 보수적으로 거절한다. 유효성을 임의 해제하거나 스냅샷을 수정하지 않는다. 새 주기 허용·수동 중단 확인·장시간 작업 재개·최대 2회 루프는 구현하지 않았다.
- 수정 후 후보 재평가가 실패하면 기존 결과의 quality_review는 보존하고 시도 기록의 재평가 결과를 판정 불가로 남긴다. 품질 검사 이력 전체를 새 결과처럼 덮어쓰지 않는다.
- 새 수정 POST의 실제 loopback HTTP/브라우저 클릭은 이번 신규 테스트에서 직접 검증하지 않았다. 기존 품질 HTTP 회귀는 통과했고 새 경로는 직접 핸들러·저장·경합으로 검증했다. 후속 작업은 이 새 흐름의 격리된 HTTP 검증이다.

관련 4개 파일만 선택적으로 커밋·푸시하고 원격 SHA와 보고서 존재를 확인한다. 업무 데이터·테스트 생성 스냅샷·백업은 Git에 넣지 않는다.
